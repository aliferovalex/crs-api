# Повторное получение объектов: состояние диагностики

Проверка выполнена 11 октября 2026 года на платформе 8.5.4.1878,
в тестовом хранилище ProtocolLab с пятью объектами. Результаты относятся
к этому эксперименту; алгоритм нативной локальной версии пока неизвестен.

## Версия 10: пакет сериализатора

При двух последовательных получениях Конфигуратор запросил все пять объектов.
После первого получения исходные версии совпадали с версиями сервера,
но локальные версии корня и двух констант, созданных сериализатором,
отличались. У языка и константы, созданной Конфигуратором, они совпадали.
Сравнивались первые 16 байтов версии: серверные дескрипторы возвращают
нулевую контрольную часть, и это наблюдалось также у штатных объектов.

У двух созданных сериализатором констант была неверная позиция 0 вместо
1 и 2. Код формирования новых пакетов исправлен; уже сохранённые позиции
этим исправлением автоматически не меняются.

## Версия 11: контрольный пакет Конфигуратора

Конфигуратор подготовил помещение всех пяти объектов с комментарием корня
`CRS native version sync`. Перехваченный штатный пакет был отправлен серверу
один раз от того же пользователя после проверки версии и собственных захватов.
Сервер создал версию 11. Позиции констант стали 0, 1 и 2;
сохранённые идентификаторы локальных версий совпали с переданными.

Тела языка и трёх констант в штатном пакете побайтно совпали с версией 10.
В корне изменились комментарий и представление одного вложенного блока свойств.
Захваты после помещения освобождены на сервере. Конфигуратор, получивший
ошибку перехватывающего прокси вместо ответа помещения, продолжал показывать
объекты захваченными; для контрольного получения включён флажок,
разрешающий получать захваченные объекты.

Два следующих запроса получения снова содержали все пять объектов.
При втором запросе исходные версии всех объектов совпали с сервером,
а локальные версии совпали у языка и всех трёх констант. Локальная версия
корня снова отличалась. В обоих ответах тела всех пяти объектов побайтно
совпали с содержимым штатного пакета версии 11. Следовательно, сервер
не изменил эти тела при сохранении или последующей выдаче.

Разделы `requested`, `required`, `missing`, `added`, `changed`, `moved`,
`unprocessed`, `names`, `dependences` результата обоих запросов были пустыми,
но контейнер снимков содержал пять объектов. Сам факт передачи всех снимков
не доказывает изменение каждого объекта: нужно учитывать параметры
штатной команды получения. Пользователь подтвердил, что в диалоге нет
флажка «Получать только изменённые объекты». Точная причина повторной
передачи всех снимков остаётся открытой.

## Что пока не подтверждено

- Случайный UUID и CRC32 тела не воспроизводят нативную локальную версию.
- Контрольное помещение исправило расхождение версий констант, но не доказывает
  устранение повторного получения или корректность версий нового пакета сериализатора.
- Причина пересчёта версии корня после штатного получения не установлена.
- Ошибка `LazyDevDepotConfigMngr.cpp (1792)` наблюдалась при отключении
  и повторном подключении в одном сеансе; после перезапуска работа продолжалась.
  Связь этой ошибки с форматом пакетов не доказана.

Перехваченные запросы с авторизацией и учётные данные остаются вне репозитория.

## Дополнительная проверка CF и запроса получения

После закрытия Конфигуратора сохранены CF локальной конфигурации и CF версии 11
из хранилища. Бинарные контейнеры прочитаны в памяти кодом v8unpack.
Из общих файлов различались только тело корня и служебные файлы `version`,
`versions`. В теле корня обнаружен один участок: таблица в позиции
`/0/3/1/1/78` содержит записи с числовыми ключами 100–103.
Серверный порядок — 100, 101, 102, 103; локальный — 103, 102, 101, 100.
Значения по каждому ключу одинаковы (1, 1, 0, 0 соответственно).
После сортировки этой таблицы по ключу деревья сериализации совпадают полностью.
Назначение таблицы не установлено; менять её значения для исправления версии
оснований нет. Первоначальные позиционные различия значений оказались
следствием перестановки записей, а не изменением свойств.

Штатное пакетное обновление той же базы с `-revised` сообщило о локальных
отметках захвата при отсутствии серверных захватов и получило пять объектов.
Следующий запуск без `-revised` также получил пять объектов, но сообщения
о несогласованных захватах больше не было. В обоих запросах локальные версии
детей совпали с сервером; у корня осталось расхождение.

Выполнен отдельный контрольный RPC `DevDepot_updateObjects`, не записывающий
изменений в информационную базу: в штатном запросе локальные и исходные версии
всех пяти объектов заменены на точные серверные значения, включая контрольную
часть, и согласованы с бинарным графом. Список явно запрошенных объектов
сохранён. Сервер опять вернул снимки всех пяти объектов. Идентификатор версии
хранилища до и после вызова одинаковый.

Таким образом, несовпадение локальной версии корня **не является необходимым
условием повторной выдачи всех пяти снимков**. Этот вызов возвращает явно
запрошенные объекты даже при совпадении версий. Нельзя использовать число
полученных снимков как самостоятельную проверку корректности сериализатора
или как доказательство изменения объектов. Алгоритм формирования нативных
версий и влияние порядка записей на него остаются отдельной задачей.

## Повторная загрузка XML в отдельные базы

Тот же XML без `ConfigDumpInfo.xml` загружен в две новые неподключённые базы
платформы 8.5.4.1878. Хранилище и рабочая база при этом не менялись.
У языка и всех трёх констант версии в новых базах совпали друг с другом.
Версии языка и изначально штатной константы совпали также с предыдущими
штатными версиями. Тела всех дочерних объектов в двух новых базах одинаковы.

У двух констант сериализатора восстановленные из XML тела семантически совпали
с сохранёнными в хранилище, но отличались переносами строк; версии тоже отличались.
Это совместное наблюдение не доказывает, что именно переносы определяют версию:
при загрузке платформа также реконструирует объект. Отдельно исправлен текстовый
формат новых констант; результат преобразования каждого из трёх XML теперь
побайтно совпадает с соответствующим штатным телом в CF.

В новых базах версии корня оказались разными. Однако различались и тела:
одно служебное число в позиции `/0/10/1/0` приняло значения 68805520 и 380965280.
Поэтому эксперимент не доказывает недетерминированность версии одинакового тела.
Назначение числа не установлено; называть его контрольной суммой оснований нет.
Остальные части разобранных тел корня совпали между новыми базами.

Офлайн проверены SHA1, MD5 с прямым и GUID-порядком байтов, варианты CRC32,
UTF-8, UTF-16, CP1251, завершения и префиксы длины, части дерева и несколько
вариантов потоков токенов: 2756 кандидатов для корня, 188 для языка и по 371
для констант. Совпадений с соответствующими штатными версиями не найдено.
Это исключает только проверенные варианты, а не все способы хеширования.

## Чистое хранилище, созданное через интерфейс Конфигуратора

Дополнительный контроль проведён в NativeGuiLab на той же платформе 8.5.4.1878.
Пользователь создал хранилище через интерфейс Конфигуратора из новой пустой базы,
без импорта CF/XML и без помещения пакетов библиотеки. Начальная версия 1
содержала два объекта: корень и язык. HTTP-обмен записан обычным прокси,
передающим запросы и ответы без тестового удержания помещений.

До изменения комментария первый запрос получения содержал совпадающие
исходные и локальные версии обоих объектов; сервер всё равно вернул два снимка.
Следующее получение вернуло те же тела. Исходные версии продолжали совпадать,
но локальная версия корня уже отличалась. Локальная версия языка совпадала.

Пользователь изменил комментарий корня с пустого значения на `Native GUI test 1`
и выполнил штатное помещение. Конфигуратор включил в пакет корень и язык;
сервер создал версию 2. Тело языка не изменилось. В корне изменился комментарий
и порядок записей уже известной таблицы в позиции `/0/3/1/1/78`:
в предыдущем серверном снимке ключи шли 103, 102, 101, 100,
а в штатном пакете помещения — 100, 101, 102, 103. Значения по ключам те же.

Два следующих обновления снова запросили и получили оба объекта. В первом
запросе версии совпали с сервером; во втором локальная версия корня отличалась,
а исходные версии обоих объектов и локальная версия языка совпали.
Тела обоих ответов побайтно совпали с отправленным штатным пакетом версии 2
и друг с другом. Во всех четырёх получениях разделы результата `requested`,
`required`, `missing`, `added`, `changed`, `moved`, `unprocessed`, `names`,
`dependences` были пустыми.

Таким образом, повторная выдача всех явно запрошенных объектов и расхождение
локальной версии корня воспроизведены **без участия сериализатора и без его
пакетов в истории хранилища**. Эти наблюдения нельзя приписывать библиотеке.
Чистый контроль не доказывает причину расхождения версии корня и не проверяет
поведение через TCP или другие версии платформы; связь с перестановкой таблицы
остаётся гипотезой. Независимые ограничения формирования нативных версий
пакетов библиотеки по-прежнему актуальны.

## Сравнение HTTP и TCP на той же базе

После закрытия интерактивного Конфигуратора сохранена исходная выгрузка
`client-gui-clean`. Затем выполнены два последовательных пакетных получения
через HTTP (прокси 18093) и два через TCP (сервер 1542) из NativeGuiLab.
Для каждого получения запущен отдельный процесс платформы 8.5.4.1878 с
`/ConfigurationRepositoryUpdateCfg -force`, без `-revised` и списка объектов.
База не отключалась от хранилища; адрес задавался параметром запуска.
После каждого шага отдельными процессами выгружены CF и XML с ConfigDumpInfo.
Параметр `-force` подтверждает добавление/удаление объектов при пакетном
обновлении, согласно [руководству платформы](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.27_Administrator_Guide/Appendix_7._Startup_command-line_options_of_1C_Enterprise/7.4._Running_Designer_in_batch_mode/7.4.15._Configuration_repository_operations/?language=en).

Во всех четырёх штатных журналах явно указано получение конфигурации и языка.
Все процессы завершились успешно, обе выгрузки каждого шага созданы.
Локальные тела обоих объектов побайтно совпали с исходной выгрузкой,
а версии из ConfigDumpInfo остались одинаковыми во всех пяти состояниях.
HTTP-ответы по-прежнему содержали оба неизменных серверных снимка версии 2.
Трафик TCP не декодировался; факт получения по TCP подтверждён штатным журналом,
а результат — выгрузками, а не анализом бинарного сетевого протокола.

Локальное тело языка совпало с серверным HTTP-снимком. Тело корня отличалось
от него только порядком записей таблицы `/0/3/1/1/78`; после сортировки по ключу
разобранные деревья полностью совпали. Эти же локальные тела сохранялись
после обоих TCP-получений. Таким образом, для проверенной пакетной операции
повторное получение и сохранённое отличие корня не зависят от HTTP-прокси.
Эксперимент не доказывает причину алгоритма локальной версии, не заменяет
сравнение интерфейсной операции через TCP и не проверяет другие платформы.

## Контроль на ветке 8.5.1 и проверка библиотеки

Пользователь повторил штатный интерфейсный тест в отдельных новых базах и
хранилищах: на 8.5.1.1150 при файловом подключении второе обновление объекты
не получает, а на 8.5.4.1878 при файловом подключении получает снова.
После установки клиента и сервера 8.5.1.1529 проведён такой же тест через TCP
в новом ManualClean8511529Lab: повторного получения также нет.
Эти результаты получены по сообщению пользователя, а не по записи файлового
или TCP-протокола. Они указывают на различие поведения веток платформы,
но не устанавливают точный релиз появления или причину различия.

Для интеграционного теста библиотеки создана отдельная HTTP-публикация с
wsisapi.dll 8.5.1.1529, направленная на crserver.exe той же версии.
В ManualClean8511529Lab прошли авторизация, создание тестового разработчика,
получение корня и языка, описание обоих объектов по UUID, захват и отмена.
Проверены неизменность состояния при получении, неизвестный UUID, отказ для
устаревшего описания, сохранение чужого захвата и повторная отмена свободного
объекта. Номер версии корня до помещения — 2, языка — 1.

Нативный запрос помещения 8.5.1.1529 с одним изменённым корнем записан
удерживающим прокси: сервер его не получил, прокси вернул 503.
Метод `ПоместитьОбъект` отправил сохранённый пакет от администратора и создал
версию 3. Полученное тело корня (6816 байт) побайтно совпало с телом из
нативного пакета; комментарий `CRS API 8.5.1 put test` подтверждён.
Чужой захват и устаревшее описание отклонены до успешного помещения,
повторное использование пакета отклонено после него, собственный захват
освобождён. Повторное описание по UUID подтвердило версии корня 3 и языка 1.

Таким образом, проверенные методы библиотеки работают с 8.5.1.1529 на этом
хранилище. Помещение проверено с **пакетом штатного Конфигуратора**;
сериализатор из XML остаётся ограниченным 8.5.4.1878 и в этом тесте не вызывался.
Совместимость сериализатора с 8.5.1 и его алгоритм нативных версий этим
экспериментом не подтверждены. После получения версии 3 пользователь повторил
интерфейсное обновление без правок: Конфигуратор объекты снова не получает.
Таким образом, помещение библиотекой сохранённого нативного пакета в этом
тесте не вызвало повторной загрузки неизменённых объектов.

## Адаптация XML-сериализатора к 8.5.1.1529

Добавлен отдельный профиль формата: таблица свойств корня имеет счётчик 76
и длину 77 вместо счётчика 79 и длины 81 в 8.5.4.1878. Поддерживаемые позиции
строковых свойств совпадают. Общие свойства 8.5.1 имеют формат 3 и содержат
UUID из InternalInfo/ContainedObject класса General; он проверяется по XML,
а не подставляется из другого хранилища. Новая константа также использует
формат общих свойств 3, без двух полей, добавленных в формате 4.

В отдельной неподключённой базе Конфигуратор 8.5.1.1529 собрал константу
из XML 2.21. Её нативное тело длиной 630 байт побайтно совпало с результатом
адаптированного сериализатора с теми же UUID и свойствами.
В ManualClean8511529Lab пакет из XML изменил комментарий на
`CRS XML 8.5.1 serializer` и поставщика на `CRS851Vendor`, создав версию 4.
Оба значения проверены в полученном снимке. Затем из XML без сохранённого
запроса помещения создана CRSAPI_XML851Constant (строка переменной длины 64),
UUID 0ddeea11-6885-43b4-b289-82a28ad5a992, версия 5. Константа, корень и язык
получены библиотекой; все тестовые захваты освобождены.

Обнаружена особенность статистики 8.5.1: после захвата неизменённого языка
запрос с objRefs=UUID вернул verNum=4, тогда как полная статистика и история
содержимого сохранили verNum=1. Для проверки актуальности библиотека использует
полную статистику на этой версии; она возвращает состояние всех объектов,
что увеличивает объём ответа в больших хранилищах. Для отмены собственного
захвата отдельный запрос по UUID получает версию операции захвата.
Владелец повторно проверяется до отправки отмены; описание содержимого
не изменяется. Отмена с номером захвата 4 проверена на том же языке.

Прошли 32 Python-теста, проверки OneScript пакета, контекста и запросов захвата,
а также повторные интеграционные проверки чтения и захвата на 8.5.1.
Сериализатор остаётся экспериментальным: UUID+CRC не является восстановленным
алгоритмом нативных версий. Приём пакетов сервером и совпадение тел не доказывают
совпадение локальных версий Конфигуратора. Повторное интерфейсное обновление
после XML-пакетов версии 5 проверяется отдельно.
