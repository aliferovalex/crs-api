# Возможности и ограничения CRS API

Библиотека взаимодействует с хранилищем конфигурации 1С по HTTP и самостоятельно
готовит нативные пакеты из XML-выгрузки Конфигуратора. Получение, захват, отмена
захвата и помещение реализованы. Сериализация поддерживает перечисленные ниже
классы и проверенные свойства; **помещение любого изменения произвольной
конфигурации пока не реализовано**.

## Совместимость и зависимости

- Основная проверенная связка клиента и сервера — **8.5.1.1529**.
- Для ветки 8.5.1 и более ранних версий 8.x выбирается общий профиль `legacy`.
  Это правило выбора, а не подтверждение совместимости с каждой старой версией.
- Для 8.5.4.1878 существует отдельный профиль `modern` с ограниченным покрытием.
  Нельзя переносить на него гарантии сериализации профиля `legacy`.
- Для остальных более новых версий профиль XML-сериализации не определён.
- Для API нужен OneScript с зависимостями проекта, для XML-сериализации — Python
  3.9+ и **v8unpack==1.2.13**. Конфигуратор во время подготовки пакета не запускается.

Зависимости Python устанавливаются из корня проекта в используемый интерпретатор:

```powershell
python -m pip install -r src/Сериализация/requirements.txt
```

Пакет из публичного `opm` может отличаться от этой ветки. Новые возможности
относятся к текущим исходникам форка.

## API хранилища

| Возможность | Состояние |
| --- | --- |
| Подключение, версия сервера, проверка существования хранилища | Реализованы |
| Создание хранилища | Реализовано; загрузка исходной конфигурации из CF/CFE не реализована |
| Пользователи | Список, поиск, создание, изменение, удаление и восстановление реализованы |
| `ПолучитьОписаниеОбъекта(UUID)` | Актуальное описание объекта, включая его версию и владельца |
| `СписокОбъектовВерсии(Номер)` | Описания объектов, изменённых в указанной версии; это не полный список конфигурации |
| `ПолучитьОбъект(Описание)` | Нативное содержимое объекта; не XML-выгрузка Конфигуратора |
| `ПолучитьВнешниеДанныеОбъекта(Описание)` | Чтение внешних потоков объекта, например текста модуля |
| `ПолучитьКлассыМетаданных(Корень)` | Каталог классов из содержимого корня; наличие класса не означает наличие его сериализатора |
| `ЗахватитьОбъект`, `ОтменитьЗахватОбъекта` | Работа с одним существующим объектом, с проверкой состояния на сервере |
| `ПодготовитьПакетИзВыгрузки` | Общий вход создания, изменения и удаления; отсутствующие дети полного XML владельца удаляются автоматически |
| `ПодготовитьПакетИзВыгрузок` | Несколько файлов существующих объектов объединяются в один пакет изменений; захваты и версии проверяются для каждого объекта |
| `ПланИзмененийКонфигурацииИзВыгрузки` | Сравнение полных папок выгрузки, список созданий, изменений и удалений, с проверкой исходных версий |
| `ПодготовитьКонфигурациюИзВыгрузки` | Отбор файлов из полной папки; поддерживаемые создания, изменения и каскадные удаления объединяются в одну версию |
| `ПоместитьПакет` | Отправка подготовленного пакета, в том числе нескольких связанных объектов |
| `ПодготовитьУдалениеОбъекта`, `ПоместитьУдалениеОбъекта` | Общий механизм удаления одного отдельно хранимого объекта по полному целевому XML владельца |
| `СписокВерсий` | Метод существует, но успешная работа на основной связке 8.5.1 требует отдельной проверки и исправления обработки ответа |

## Покрытие XML-сериализации

Публичные методы подготовки и помещения для отдельных видов метаданных
удалены. Для константы, справочника, документа, перечисления, общего модуля
или формы используется один вход:

```bsl
Пакет = Клиент.ПодготовитьПакетИзВыгрузки(
    "C:\Export\Catalogs\Товары.xml", Неопределено, "python");
Для Каждого Объект Из Пакет.СуществующиеОбъекты Цикл
    Клиент.ЗахватитьОбъект(Объект);
КонецЦикла;
Результат = Клиент.ПоместитьПакет(Пакет, "Изменение из выгрузки");
```

Класс, UUID, родитель и операция определяются по XML и контексту хранилища.
Модули и содержимое форм читаются из стандартных соседних файлов выгрузки.
Публичных обёрток с именем класса или передачей отдельных свойств больше нет;
это не расширяет перечень поддерживаемых свойств и классов. Внутренние
обработчики по плану сохраняют проверки версий, захватов и ссылок.

Внутренний Python-вход создания принимает `object_type` (класс метаданных) и
`object_xml` (полный XML объекта). Ключи XML с именами отдельных классов
удалены; класс создания задаётся явно, без значения по умолчанию.

Изменения отдельных объектов проходят через `ПодготовитьИзменениеПоПлану`
и `СериализаторОбъектаХранилища.ИзменениеПоПлану`: снимок читается общим
кодом, пакет текущей версии дополнительно запрашивается для форм, макетов
и XML со ссылочными типами реквизитов.
Выбор преобразователя корня, общего модуля, формы, макета или другого объекта
сосредоточен в сериализаторе. Прежние `ПодготовитьИзменениеФормыПоПлану`
и `ИзменениеФормыИзXML` удалены без обёрток совместимости.

Изменение справочника, его реквизитов и табличных частей выполняется через
общий вход `ПодготовитьПакетИзВыгрузки` по полному XML справочника. В Python
используется `object_change_serializer.py`: проверки снимка, версии, связей,
внешних потоков и сборка пакета общие с другими объектами. Преобразование
XML справочника и константы преобразуется общим `metadata_object_xml.py`
по профилям. Автоматическое удаление дочерних объектов использует тот же путь.
Отдельные методы создания реквизита
по имени и длине и специализированный сериализатор пакета удалены.

Основные общие преобразователи:

| Модуль | Назначение |
| --- | --- |
| `metadata_object_xml.py` | Преобразование полного XML объекта в нативное тело по проверенным профилям, включая поддержанные вложенные коллекции и ссылки |
| `object_creation_serializer.py` | Сборка пакета создания объекта, включая связанные изменения и управляемые формы |
| `object_change_serializer.py` | Сборка изменения существующего объекта по полному XML |
| `tabular_section_xml.py` | Общий преобразователь табличных частей справочников, документов, обработок и отчётов |

Общие свойства читаются напрямую в `metadata_common_xml.py`;
`inline_attribute_xml.py` обрабатывает встроенные реквизиты без промежуточного
XML константы. Различия константы, справочника и других классов хранятся
в профилях: пути свойств, шаблоны, внутренние UUID и дочерние коллекции.
Создание и изменение используют общие функции `create` и `change` модуля
`metadata_object_xml.py`. Проверяются неизменность внутренних UUID, области
владения реквизитами, ссылки и порядок отдельно хранимых детей. Изменение
существующей константы в `legacy` проходит через тот же механизм: общий XML-вход
меняет тип, синоним и комментарий, сохраняя UUID объекта и сгенерированных типов.
`InternalInfo` можно не передавать; при его наличии UUID должны совпадать с
исходным телом. Остальные свойства константы остаются ограничены профилем;
изменение на `modern` пока отклоняется явно.
`report_form_properties.py` сохраняет специфические свойства формы отчёта.
Создание формы у существующего справочника со ссылочными реквизитами использует
общую сверку исходных зависимостей. Допустимая связь, подтверждённая свойством
или нативным типом из актуальной версии, сохраняется; посторонняя живая связь
не разрешается автоматически. Пакет текущей версии передаётся также при создании
формы, чтобы сверить типы родителя и разрешить ссылки её содержимого.
По HTTP и обратной загрузкой в Конфигуратор проверено создание формы с модулем
у справочника со ссылкой на перечисление и составными реквизитами. Исходные связи
родителя сохранились; его тело изменилось только в коллекции форм, посторонние
объекты и потоки остались прежними.
Нативные примитивы находятся в `native_metadata.py`, читатели updateInfo —
в `metadata_context.py`, сверка снимка с контекстом — в `serialization_context.py`.
Корень разделён на преобразование XML (`configuration_xml.py`) и сборку пакета
(`configuration_serializer.py`). `object_creation_serializer.py` отвечает
за сборку создания и использует общий преобразователь тела объекта.

[Карта модулей и вызовов](module-map.md) описывает назначение всех модулей Python
и OneScript. Она формируется из исходников инструментом `tools/build_module_map.py`;
проверка актуальности: `python tools/build_module_map.py --check`.

Несколько существующих объектов можно изменить одним помещением:

```bsl
Пути = Новый Массив;
Пути.Добавить("C:\Export\Configuration.xml");
Пути.Добавить("C:\Export\InformationRegisters\ИмяРегистра.xml");
Пакет = Клиент.ПодготовитьПакетИзВыгрузок(Пути, "python");
Для Каждого Объект Из Пакет.СуществующиеОбъекты Цикл
    Клиент.ЗахватитьОбъект(Объект);
КонецЦикла;
ПомещенныеОбъекты = Клиент.ПоместитьПакет(Пакет, "Изменение конфигурации");
```

Групповой вход принимает 1–256 файлов описаний существующих объектов, включая
поддерживаемые сопутствующие модули и содержимое форм. Он использует прежние
преобразователи, проверяет нативные графы и SHA-1 манифесты и собирает один
контейнер с отдельными версиями объектов и потоков. Повторные UUID, смешение
хранилищ или версий и несогласованные описания отклоняются. Результат помещения
группы — массив описаний, подтверждённых одной версией хранилища.

Вход для массива файлов объединяет изменения существующих объектов. Для
совмещения изменений с удалениями используется вход полной папки ниже:
он строит конечные тела и граф, а не складывает отдельные пакеты удаления.
Поддерживаемые новые объекты верхнего уровня подключены к этому же конечному графу.

Полная папка обрабатывается отдельным входом:

```bsl
План = Клиент.ПланИзмененийКонфигурацииИзВыгрузки(
    "C:\Export\Target", "C:\Export\Baseline", "python");
Пакет = Клиент.ПодготовитьКонфигурациюИзВыгрузки(
    "C:\Export\Target", "C:\Export\Baseline", "python");
```

`Baseline` — сохранённая полная иерархическая XML-выгрузка текущей конфигурации
хранилища с `ConfigDumpInfo.xml`. Её нельзя редактировать. Версии всех отдельно
хранимых объектов и внешних потоков сверяются с сервером; устаревшая исходная
выгрузка отклоняется. `Target` — её изменённая копия. Изменения определяются по
содержимому файлов: `ConfigDumpInfo.xml` целевой папки может остаться прежним.

Обход проверяет дерево по карте метаданных, наличие всех описаний детей, UUID,
родителей и сопутствующих файлов. Изменение модуля, `Form.xml` или файла макета
относится к его объекту. Неизменённые классы не требуют преобразования. Изменённые
неподдерживаемые файлы, смена класса или владельца существующего UUID и неполные
выгрузки отклоняются. Переименование подключено к общему преобразователю объектов,
общим модулям, управляемым формам и поддержанным видам макетов. Для всех 21 класса
владельцев форм общие поля Name, Synonym и Comment изменяются отдельно с сохранением
остального нативного тела. Неподдержанные свойства владельца должны оставаться
неизменными; требуется исходный XML. Имя самой конфигурации подключено к входу
полной папки. Переименование владельцев со сложными зависимостями ещё требует
расширения преобразования ссылок и проверки платформой. Для ExternalDataSource
подключены отдельно хранимые коллекции Table и Cube; встроенные Function остаются
неподдержанными. Сценарии переименования вложенных владельцев и изменения их
квалифицированных ссылок ещё требуют проверки.

Общий обработчик существующего владельца — `metadata_owner_change`. Реестр
`metadata_owner_profiles` объединяет 21 владельца форм и внешний источник данных,
который сам форм не содержит. Подключение контейнера не означает поддержку
создания этого класса либо преобразования всех его свойств. Создание внешнего
источника, новых таблиц и кубов, изменение встроенных Function пока не подключены.
Из полной целевой XML-выгрузки автоматически определяется удаление таблиц и кубов
внешнего источника вместе с их потомками, включая формы и таблицы измерений куба.
Через HTTP одним пакетом удалены таблица и куб с потомками; нативное тело владельца
и вся обратная выгрузка совпали с независимой сборкой Конфигуратора 8.5.1.1529.
Все посторонние члены CF сохранились побайтно. Редактор проверяет UUID владельца,
класс, счётчики, позиции и регистрацию детей; изменяет только соответствующие
списки UUID. Остальные свойства и встроенные функции должны оставаться прежними.
Нативные образцы и проверки — `tests/fixtures/external_source_collections_851.json`
и `tests/test_external_source_collections.py`. После удаления последнего ребёнка
пустой ChildObjects сравнивается без форматирующих отступов; текстовые свойства
по-прежнему сравниваются с сохранением пробелов.

Общие поля владельцев обрабатывает `metadata_common_xml.patch`: исходные Name,
Synonym и Comment сверяются со снимком, изменяются только их нативные токены;
остальное тело и BOM сохраняются. Имя разрешено менять только при явном разрешении
плана полной выгрузки. Отдельный импорт XML Конфигуратором 8.5.1.1529 подтвердил
изменение синонима и комментария всех 21 класса; фикстура независимых нативных
результатов — `tests/fixtures/owner_common_properties_851.json`. Проверки сохранения
всего остального тела, обратимости, отказа при устаревшем исходном XML и
неразрешённом переименовании — `tests/test_owner_common_properties.py`.

При переименовании владельца сравнение исходного и целевого XML учитывает
производное имя GeneratedType в InternalInfo и сегмент имени владельца в собственных
ссылках xr:Field. Префикс типа, UUID сгенерированных типов и оставшийся путь поля
по-прежнему должны совпадать. Это позволяет менять Name без пересборки неизвестных
свойств владельца; произвольные текстовые ссылки на переименованные другие объекты
не считаются эквивалентными автоматически.

Через HTTP одной версией проверены переименования 16 корневых владельцев форм:
12 классов с полными профилями и четырёх без полного XML-преобразователя —
BusinessProcess, CalculationRegister, ExchangePlan и FilterCriterion. Независимый
импорт Конфигуратора 8.5.1.1529 подтвердил изменение только Name в каждом теле;
результат API совпал с полными нативными телами и всей XML-выгрузкой. Все UUID,
внешние потоки форм и остальные члены CF сохранились. Четыре нативных образца
неполных профилей закреплены в `tests/fixtures/opaque_owner_rename_851.json`.
Обновление текстовых ссылок BusinessProcess.Task и
CalculationRegister.ChartOfCalculationTypes при переименовании соответствующей
задачи или плана видов расчёта подключено через `opaque_owner_references`.
Изменённые ссылки разрешаются по исходному и итоговому индексам: класс, владелец,
родитель и UUID цели должны совпадать, смена имени должна быть разрешена общим
планом, а исходный UUID — совпадать с проверенным полем нативного тела. Для
сравнения полного XML меняется только представление этих известных ссылок;
произвольные свойства по-прежнему защищены. Смена самого UUID цели этим механизмом
не поддерживается.
Через HTTP одним пакетом переименованы задача и план видов расчёта и обновлены
входящие XML-ссылки. Полная обратная выгрузка совпала с независимой нативной сборкой
Конфигуратора 8.5.1.1529; тела бизнес-процесса и регистра расчёта, все потоки и
посторонние члены CF сохранились побайтно. Нативные образцы и проверки отказов —
`tests/fixtures/opaque_reference_renames_851.json` и
`tests/test_opaque_reference_renames.py`. Остальные ссылочные свойства неполных
профилей требуют сопоставления и проверки.

Переименование владельца одновременно с созданием или изменением его формы
подключено к входу полной выгрузки. `managed_form_profiles.binding_owner` принимает
итоговое имя только при явном разрешении общего сборщика; UUID владельца и UUID
каждой категории сгенерированных типов должны совпадать с источником. XML формы
преобразуется с итоговым именем владельца, исходные снимки и версии остаются прежними.
Отдельный вызов без разрешения переименования сохраняет проверку имени.
В отдельном хранилище через HTTP одним пакетом переименован документ, изменены
заголовок поля и модуль существующей формы с главным реквизитом DocumentObject,
создана новая привязанная форма и назначена основной. Тела документа и обеих форм,
весь XML и модули совпали с независимой сборкой Конфигуратора 8.5.1.1529; UUID

новыми регистрами. В одиночном XML-входе сохраняется параметр `СвязанныеXML`.
Реквизиты и колонки форм могут ссылаться на одновременно создаваемые справочники,
документы и перечисления. Проектные значения перечислений в списках выбора также
читаются из итогового тела, включая новые значения изменяемого перечисления.
Ссылки СКД на сгенерированные типы новых объектов разрешаются тем же каталогом
нативных определений. Сначала создаются определения всех новых владельцев,
затем собираются формы и макеты; UUID типов без `InternalInfo` назначаются один
раз. Это поддерживает ссылки на себя и вперёд независимо от порядка файлов.
Проверено созданием справочника, документа и перечисления без `InternalInfo`
вместе с тремя собственными формами, общей формой и тремя СКД. Штатная загрузка
и обратная выгрузка подтвердили UUID ссылочных типов, значения перечисления
в списках выбора и ссылки в XML форм/СКД; остальные объекты сохранились.
Новые определения не подменяют серверные снимки: неизменённые цели читаются
из снимка или пакета версии со сверкой класса, владельца и версии; отсутствующая
в итоговой конфигурации цель отклоняется. Ссылки на стили используют тот же
проверенный источник. Прочие виды ссылочных типов форм остаются ограничены
реализованными профилями.

Свойства `Type`, встроенные реквизиты и реквизиты табличных частей используют
общий читатель скалярных, ссылочных и составных типов. `metadata_type_references.py`
разрешает `cfg:<Класс>Ref.<Имя>` только для классов с проверенными позициями
сгенерированных типов. До преобразования тел новых объектов их UUID типов
выделяются один раз и регистрируются в итоговом каталоге; поэтому поддержаны
взаимные ссылки двух новых владельцев и самоссылки без `InternalInfo`.
Ограничения коллекций сохраняются: числовой ресурс не принимает ссылочную
ветвь внутри составного типа. Обратное преобразование требует словарь имён
для каждого ссылочного UUID и отклоняет неизвестный тип.

Независимое сравнение с полной XML-выгрузкой Конфигуратора 8.5.1.1529 подтвердило
совпадение полных нативных тел справочника, документа, перечисления, константы
и параметра сеанса: взаимные ссылки, ссылки на перечисление, составные типы
и ссылочный реквизит табличной части. Пример сохранён в автоматических тестах.
Для табличных частей справочников и документов сохранено отличие схемы: `FillValue` и
`FillFromFillingValue` отсутствуют и не изменяют служебные значения шаблона.
Сквозная проверка по HTTP также подтверждена: эти пять связанных объектов
созданы одним пакетом, затем через общий одиночный XML-вход изменены составной
тип и комментарий существующей константы без передачи `InternalInfo`.
Каждый результат прочитан из хранилища, загружен в Конфигуратор и выгружен в XML:
нативные тела совпали полностью, UUID типов сохранились, посторонние объекты
и потоки остались неизменными.

При изменении объекта сверяются и зависимости: связи исчезнувших ссылочных
типов и сопоставленных свойств удаляются, сохранившиеся и непрозрачные связи
остаются. Владелец исходного ссылочного типа подтверждается его нативным телом
из снимка или пакета версии со сверкой версии; неизвестная исходная привязка
отклоняется. Пакет версии запрашивается и тогда, когда из целевого XML уже убрали
последнюю `cfg:`-ссылку. Для явного удаления отдельно хранимого объекта он также
передаётся общему преобразователю владельца.
Эта сверка изменяет граф тел, обрабатываемых `metadata_object_xml`.
Дополнительно `external_dependencies` проверяет оставшиеся внешние потоки
управляемых форм и СКД перед удалением объектов и встроенных элементов.
Ссылки могут отсутствовать в серверном графе: в таком случае проверяется само
содержимое потока из пакета текущей версии. Проверяются версии объектов и
потоков; новые потоки подставляются поверх исходных, поэтому можно убрать ссылку
и удалить её цель одним пакетом. Учитываются UUID объектов, сгенерированных типов
и значений перечислений. Строка формы, просто совпадающая с UUID, не считается
ссылкой; произвольные данные двоичных и текстовых макетов не анализируются.
Для проверяемых классов неизвестный формат потока отклоняется, а не пропускается.
Пакет версии при этой проверке читается по общему индексу один раз. Проверка
ссылок в BSL и других видах потоков сюда не входит.

По HTTP подтверждён сценарий с тремя формами и СКД, ссылающимися на перечисление:
попытка удаления с оставленными ссылками отклоняется до помещения, а после
изменения этих четырёх потоков перечисление с собственной формой удаляется
одним пакетом. Загрузка результата в Конфигуратор и обратная выгрузка подтвердили
устранение ссылок и сохранность посторонних объектов и потоков.
При переписывании XML сохраняются как именованные пространства имён, так и
пространство по умолчанию: непредварённые префиксом значения QName вроде
`xsi:type="DataSetQuery"` в СКД не теряют своего значения.

Наличие форм само по себе больше не запрещает удаление реквизитов и табличных
частей справочника. В одиночном XML-входе удаление встроенных элементов проверяется
по текущим потокам; используемый реквизит отклоняется, неиспользуемый можно удалить
с сохранением формы. В общей папке выгрузки реквизит и использующее его поле формы
можно удалить одним пакетом. Исправленные потоки проверяются после сборки всех
изменений. При удалении табличной части дополнительно учитываются её собственные
сгенерированные типы таблицы и строки, а не только UUID элемента метаданных.
По HTTP проверены оба пути: неиспользуемый реквизит удалён одиночным методом
при неизменной форме; используемый реквизит удалён вместе с полем формы общей
сборкой. Оставленная привязка отклоняется в обоих входах. Обратная загрузка

синонимы и назначения форм не требуют снимков всех неизменённых форм владельца.

изменений нет, `ПодготовитьКонфигурациюИзВыгрузки` возвращает `Неопределено`.

Определяемые типы используют общий преобразователь `metadata_object_xml` и профиль
`definedtype_layout_851.json`. Описание `Type` пересобирается целиком; при изменении
без `InternalInfo` сохраняются исходные сгенерированные идентификаторы.
Ссылка `<v8:TypeSet>cfg:DefinedType.ProbeAlias</v8:TypeSet>` преобразуется в
`{"Pattern", {"#", UUID сгенерированного типа}}`. UUID объекта метаданных
используется отдельно для связи зависимости. Разрешение работает по проверенному
снимку существующего объекта либо по предварительному объявлению нового объекта
в общем пакете. Скалярный и составной профили и параметр сеанса со ссылкой совпали
с независимыми нативными телами Конфигуратора 8.5.1.1529.
В отдельном тестовом хранилище через HTTP создан общий пакет двух типов и
параметра сеанса. Затем изменена длина строки типа с 64 на 96: сгенерированные
UUID сохранились, зависимый параметр и посторонние члены CF остались побайтно
прежними. Каждый результат загружен Конфигуратором и выгружен обратно в XML.
Циклические определения и произвольные комбинации типов ещё не проверены.

Дополнительные реквизиты управляемой формы поддерживают тот же `TypeSet`.
Независимая компиляция общей формы подтвердила UUID типов и связи нативного
описателя: владелец и использованные определяемые типы имеют флаг связи `1`.
Создание формы библиотекой воспроизвело эти связи; при последующем удалении
реквизита и поля по полному `Form.xml` исчезла ровно связь неиспользуемого типа.
Сохранились оставшийся `TypeSet`, весь изменённый модуль и остальные члены CF.
Оба результата проверены через HTTP, загрузку CF и обратную XML-выгрузку.
Общий обработчик форм сохраняет непрозрачные связи, а удаляет только связи,
подтверждённые UUID сгенерированного типа в исходном потоке и его актуальным
снимком или хранилищем версий. Основной реквизит формы через определяемый тип
отдельно не поддержан.

Регламентные задания используют общий преобразователь объекта и профиль
`scheduledjob_layout_851.json`. Общее правило ссылки на метод разделяет
`CommonModule.ProbeJobs.Run` на реальный UUID модуля и имя процедуры; обратное
преобразование восстанавливает квалифицированное имя. Числовые свойства читаются
общим обработчиком целых значений в диапазоне 0..2147483647. Оба края диапазона
подтверждены независимой компиляцией; описание и ключ допускают пустые строки.
При помещении из полного XML пересобирается всё описание задания.

Нативные описатели заданий не содержат связь с модулем из `MethodName`.
Это отмечено в общем профиле ссылки через `relation_flag: null`: сборщик не
добавляет отсутствующую у платформы связь. Вместо неё проверка удаления читает
сопоставленные ссылки из актуальных нативных тел сохранённых заданий. Удалить
используемый модуль можно после изменения метода или удаления самого задания.
Проверка также учитывает итоговое тело задания при атомарном изменении пакета.
Отказ удаления используемого модуля проверен на реальном тестовом хранилище
через общий вход подготовки; ошибка получена до захвата и помещения.
Создание и изменение проверены через HTTP в отдельном хранилище: оба XML совпали
после нативной загрузки CF и обратной выгрузки, общий модуль и другие задания
остались побайтно прежними. Расписание `Schedule`, свойства расширений и запуск
регламентного задания этим сценарием не покрыты.

Профиль документа включает 22 скалярных свойства, сопоставленных по 26 независимым
нативным вариантам Конфигуратора 8.5.1.1529. Это стандартные команды,
тип, длина и допустимая длина номера, периодичность номера (без периода, год,
квартал, месяц, день), проверка уникальности, автонумерация, создание при вводе,
поиск по строке и полнотекстовый поиск, разрешение обычного и оперативного
проведения, удаление и запись движений, привилегированное проведение/отмена,
включение справки, история выбора и история данных с двумя дополнительными
флагами. Полный XML преобразуется общим обработчиком скалярных свойств;
неизвестные значения перечислений отклоняются.

Привязки форм документа переведены на общий профиль `managed_form_bindings`:
`Number` получает строковый либо числовой тип из нативного владельца,
`Date` сохраняет тип даты, реквизиты и табличные части читаются общим механизмом.
Две независимо скомпилированные формы с полями номера и даты подтвердили
преобразование всего `Form.xml`. Через HTTP в отдельном хранилище созданы
все 26 вариантов документов и обе формы; нативные тела документов и XML
совпали после чтения CF из хранилища и загрузки Конфигуратором.
Следующим общим пакетом изменены свойства всех 26 документов. Формы
автоматически пересобраны при смене номера со строки на число и обратно,
без правок `Form.xml`. Обратная нативная выгрузка подтвердила целевой XML,
сохранение сгенерированных UUID и неизменность постороннего содержимого CF.
Настройка заполнения последовательностей и другие неописанные свойства ещё
не подключены; выполнение проведения и поведение нумерации в режиме предприятия
этой проверкой не подтверждаются.

Списки `InputByString` и `DataLockFields` документа преобразуются тем же
`metadata_field_lists`, что и у справочника. Состав и порядок берутся из полного
XML. Номер кодируется стандартным селектором `-2`, дата — `-3`, непосредственный
реквизит — его UUID. Поиск разрешён по номеру и индексируемым реквизитам;
дата допустима только в списке блокировок. Для реквизита блокировки индекс
не требуется. Номер нулевой длины исключается из обоих списков и контекста
привязок формы; дата при этом сохраняется. Имена чужих владельцев, отсутствующие
поля, дубли, поиск по дате и неиндексируемому реквизиту отклоняются до упаковки,
включая обратное чтение нативного тела.
Если раздел списка отсутствует в XML, проверяется и оставшееся значение
нативного шаблона: оно не может ссылаться на отключённое поле. Поэтому для
документа без номера нужен явный допустимый список поиска, в том числе пустой.
Восемь независимо скомпилированных вариантов подтвердили полные нативные тела
и обратный XML. Создание всех вариантов проверено через общий HTTP-вход
в отдельном хранилище с чтением CF, нативной загрузкой и повторной XML-выгрузкой.
Затем общим пакетом изменены все восемь документов: состав и порядок списков,
индексация, отключение и восстановление номера. Повторная нативная выгрузка
подтвердила полный целевой XML, сохранение UUID реквизитов и сгенерированных
типов, неизменность посторонних членов CF.
Вложенные пути, остальные стандартные поля и индексация с дополнительным порядком
пока не подключены; работа блокировок в режиме предприятия отдельно не проверена.

Нумераторы документов подключены к общему входу создания и изменения.
XML-класс `DocumentNumerator` соответствует классу хранилища
`DocumentNumerators`; соответствие используется при декларации, чтении,
изменении, обратном экспорте и разрешении ссылок. Нумератор не имеет

Версии неизменённых потоков владельца и оставшихся команд сохраняются. В полной
папке выгрузки отсутствие файла модуля оставленной команды очищает только её модуль;
отсутствие самой команды в XML удаляет команду вместе с модулем. Неизвестные
изменённые или удалённые сопутствующие файлы вызывают ошибку подготовки.
Удаление команд обработки и отчёта проверено через HTTP и обратную выгрузку CF:
команды и потоки исчезли, остальные нативные данные сохранились без изменений.
HTTP-шаблоны URL и их методы, Web-операции и их параметры используют тот же
`inline_metadata_xml`, что свойства команд. Профили задают пути общих свойств,
строк, перечислений, XDTO QName и вложенных коллекций. При подготовке передаётся
полный XML сервиса: отсутствующие вложенные элементы удаляются, UUID проверяются
по всему дереву. Перенос существующего UUID между родительскими коллекциями
пока отклоняется. Модуль сервиса читается из `Ext/Module.bsl` и записывается
в поток `<UUID сервиса>.0` через общий сборщик модулей.
Все 18 значений `HTTPMethod` из схемы 2.21, направления Web-параметров
`In`, `Out`, `InOut` и три режима блокировок сопоставлены с независимой
нативной компиляцией. Для XDTO поддержаны 46 встроенных типов пространства
`http://www.w3.org/2001/XMLSchema`: строки и их производные, булево, числовые
типы, даты, время, длительность, двоичные данные, URI, QName и общие типы.
Список имён закреплён в общем `xdto_types_851.json` и проверен независимой компиляцией
46 пар «возвращаемый тип операции / тип параметра». Префикс XML разрешается по
URI, а не по буквальному имени `xs`; неизвестные URI, имена типов и несвязанные
префиксы вызывают ошибку. Дополнительно по сохранённой нативной демобазе
8.5.1.1529 сопоставлены `ValueStorage` пространства `http://v8.1c.ru/8.1/data/core`,
`SpreadsheetDocument` пространства `http://v8.1c.ru/8.2/data/spreadsheet` и
`DeliverableNotificationSubscriberID` пространства `http://v8.1c.ru/8.3/data/ext`.
Имена пользовательских типов читаются из полных файлов пакетов. Для Web-сервиса
доступны типы выбранных пакетов и транзитивных импортов. Циклы импортов
обходятся однократно; неизвестные импорты, повторяющиеся пространства имён
и дубли имён типов отклоняются. Локальные проверки пользовательских ссылок
ещё не подтверждены независимой нативной компиляцией и серверным циклом.
`xdto_type_xml` используется общим преобразователем встроенных метаданных.
Префиксы разрешаются в области конкретного XML-элемента; локальные объявления
и повторное использование одного префикса для разных URI сохраняются при
подготовке полного пакета, а не сводятся к одному глобальному словарю.
Свойство `XDTOPackages` читается целиком через `metadata_value_list_xml`: ссылки
на объекты пакетов и строковые пространства имён записываются в две нативные
коллекции. Ссылки разрешаются по окончательному индексу объектов и входят в граф
зависимостей. Снятие выбора пакета удаляет подтверждённую исходным снимком
зависимость, если она больше не используется. Непустые подписи и ненулевые
флажки элементов этого списка пока отклоняются. Для `ReuseSessions` сопоставлены
`AutoUse` и `DontUse`; режим `Use` ещё не проверен.
Полное тело Web-сервиса из демобазы с шестью операциями совпало побайтно с
сохранённой нативной компиляцией. Проверены обратный XML-экспорт, изменение
списка пространств, добавление и удаление зависимости от XDTO-пакета. Локальная
сборка полной выгрузки также проверяет одновременное создание нового пакета
и ссылающегося на него Web-сервиса, включая полный файл пакета и модуль сервиса.
Серверный цикл этих новых сочетаний ещё не подтверждён.
Создание обоих сервисов с полными деревьями и модулями проверено помещением по HTTP
и обратной выгрузкой CF в Конфигураторе 8.5.1.1529: полные нативные тела побайтно
совпали с независимой компиляцией XML, тексты обоих модулей сохранились, остальные
объекты и потоки не изменились. Следующее помещение проверило изменение шаблона
URL и обработчика, добавление нового маршрута и метода, удаление старого метода,
замену полного модуля HTTP-сервиса и замену Web-операций на 46 операций с
параметрами встроенных типов. После обратной загрузки полные тела обоих сервисов
совпали с независимой компиляцией, тексты модулей сохранились, посторонние данные
не изменились. Запрет переноса существующего UUID между операциями проверяется
автоматическими тестами. Публикация сервисов, генерация WSDL и вызов обработчиков
этими проверками не охватываются.
Описание XDTO-пакета преобразуется общим `metadata_object_xml`, а полный
`Ext/Package.bin` читается через `object_file_content` и передаётся в поток
`<UUID пакета>.0` без пересборки внутреннего XML. Файлы и суффиксы потоков задаёт
реестр профилей; отдельного сборщика пакета помещения XDTO нет.
В JSON данные файлов передаются по роли, например `file_data.Package`, а имя
`Package.bin` хранится в профиле: это совместимо со структурами OneScript.
Чтение реестра и цикл OneScript → Python → OneScript проверяются отдельным тестом.
Проверяются наличие обязательного файла, XML и совпадение `targetNamespace` с `Namespace`
описания, объявления типов и пространства имён импортов. Импорты разрешаются
по окончательному каталогу пакетов полной выгрузки либо по текущим данным
хранилища. Для чтения исходных файлов проверяются версии объектов и внешних
потоков; скомпилированное целевое тело не подменяет исходный снимок. Отсутствие
обязательного файла не означает очистку: для удаления пакета нужно удалить сам
объект из коллекции корня. Независимая компиляция Конфигуратором 8.5.1.1529
подтвердила тело метаданных и побайтное совпадение файла с нативным потоком.
Подготовка создания, изменения полного файла и сохранение посторонних потоков
покрыты автоматическими тестами. Сравнение полных выгрузок обнаруживает изменение
только `Package.bin`, даже если XML описания не менялся; файл проходит до единственного
итогового пакета. Изменение содержимого пакета, на который уже ссылаются другие
объекты, требует полной выгрузки: проверяются ссылки неизменённых Web-сервисов
на удалённые типы и выбранные пакеты. При удалении импорта убирается только
зависимость, подтверждённая исходным файлом; прочие связи сохраняются.
Проверка внутренней схемы всех свойств XDTO, ограничений типов и всех QName
внутри файла пакета пока не реализована. Серверный цикл для XDTO-пакета
ещё не подтверждён.
По HTTP проверено изменение обработки и отчёта с реквизитами и табличными частями,
затем изменение их управляемых форм с полями и таблицами. Обратная выгрузка
подтвердила пути данных и сохранность посторонних объектов, модулей и потоков.
Ссылочные типы и значения разрешаются только там, где реализовано соответствующее
правило контекста; общей поддержки всех описаний типов пока нет.

### Права ролей

Свойства роли поддержаны общим преобразователем метаданных. `role_rights_xml`
компилирует целый `Ext/Rights.xml` в нативный поток: таблицы UUID и состояний,
полные условия RLS, шаблоны и три флага. Он подключён к общему механизму
файлов объекта, созданию и изменению роли, отдельной подготовке по XML и
помещению полной конфигурации. Исходный XML не отправляется серверу как
готовый нативный поток.

Для ссылок нужна иерархическая XML-выгрузка с `Configuration.xml` и описаниями
упомянутых объектов. Подготовка отдельной роли автоматически читает её из этой
папки и передаёт только определения упомянутых объектов, полей RLS и предков.
При помещении полной конфигурации используется общий итоговый индекс, включая
новые объекты. На отдельном пути определения дополнительно сверяются с классами,
именами, родителями и UUID встроенных элементов текущего контекста хранилища.
Отсутствующие, неизвестные стандартные и пока неподдержанные варианты вложенных ссылок отклоняются.

При полной подготовке `role_dependencies` сравнивает UUID описаний исходной и
целевой выгрузок. Если исчезнувший UUID присутствует в исходных связях сохраняемой
роли, её неизменённый `Rights.xml` добавляется в общий план с причиной
`metadata_reference_changed`. Файл не переписывается: его имена разрешаются заново
по итоговым определениям. Роль входит в список требуемых снимков и захватов,
пересобирается и помещается вместе с владельцем одним пакетом.
Уже выбранные роли не дублируются; изменения только модулей не запускают эту проверку.
Без полного целевого файла прав такая автоматическая пересборка отклоняется.
Проверено на замене UUID реквизита табличной части при сохранении полного имени:
общий API поместил владельца и роль, Конфигуратор загрузил CF, XML роли остался
прежним, а нативный поток использовал новый UUID. Поменялись только тело владельца,
поток роли и служебный список версий. Если целевое XML-имя больше не существует,
пересборка не удаляет права молча — целевой файл должен описывать конечный состав.

`object_file_content.convert` возвращает для каждого файла `Content(data, relations)`:
готовые байты и полный набор связей, которыми управляет этот файл, либо `None`,
если связи тела должны сохраниться. Для роли целевой файл заменяет прежние
ссылки прав и сохраняет обязательную связь с родителем; замена пустым файлом прав
удаляет старые связи. Если файл не передан, существующие потоки и связи сохраняются.
Удаление самого файла из полной выгрузки требует явного конечного содержимого.

Для восстановления соответствия имён прав и UUID есть инструмент
`tools/map_role_rights.py`. Он принимает JSON-массив наблюдений вида
`{"xml": {"Read": true}, "native": {"UUID права": 1}}`, пересекает кандидатов
по значениям и выдаёт подтверждённые соответствия, неоднозначности и противоречия.
Порядок прав не используется; два имени не могут молча получить один UUID.
Уже определённые UUID исключаются из кандидатов других прав до стабилизации;
при противоречиях дальнейшее распространение прекращается.
В нативном наблюдении `1` означает разрешение, `-1` — запрет.
Вместо словаря `native` можно передать строку полной нативной таблицы:
`role_rights_native` читает версию `0` (маркер и ненумерованный список пар)
и версию `1` (маркер, число прав и отдельные матрицы ограничений). Матрицы сохраняются целиком
при обратной сборке.

`role_restrictions_xml` преобразует полные списки условий одного права и все
шаблоны роли. Текст условий не разбирается: сохраняются запрос, кавычки и переводы
строк. Для ограничения только отдельных полей добавляется нативная строка
для остальных полей; при обратной выгрузке она снова становится неявной.
Имена полей разрешаются в нативные пути через переданный контекст; общий
контекст обычных непосредственных полей реализован в `role_metadata_context`.
С независимыми сохранёнными данными
совпали четыре полных шаблона, два общих условия и матрица ограничения ресурса
регистра, включая неявную строку. Другие классы полей требуют расширения контекста.
Массовая проверка на 334 ролях сопоставила 1177 полных шаблонов; все 1511 нативных
матриц условий сохранились после обратного XML-экспорта, чтения XML и повторной
сборки. У 332 ролей содержимое матриц совпало с исходной XML-выгрузкой напрямую.
В двух остальных обнаружены четыре пустые нативные записи без XML-условий
и один старый текст с дополнительными CR. Новый XML-экспорт сохраняет такие CR
через ссылки на символы; независимая компиляция целевого XML для этого старого
варианта ещё не проверена. Проверка не подтверждает привязку UUID прав к именам
или поддержку всех заголовков объектов роли.

`metadata_definitions` строит индекс итоговых XML-описаний по коллекциям карты
схемы: включает хранимые объекты, реквизиты, табличные части, операции, параметры
и другие вложенные элементы. Для каждого известны полное имя, фактический UUID,
родитель и UUID хранимого тела. Вложенному элементу не создаётся фиктивная запись
хранилища. Полная регистрация хранимых детей, уникальность имён/UUID и циклы
владения проверяются. Распознавание имени не включает сериализатор класса.
На сохранённой рабочей выгрузке построен индекс 42 982 элементов, включая
13 557 хранимых объектов.

`role_metadata_context` формирует и проверяет обычные заголовки ссылок по этому
индексу и общему профилю из 31 вида элементов. Обратное чтение проверяет UUID
и признак поля. `Field` связывает поле RLS с реальным определением метаданных:
для обычного поля используется его UUID, для стандартного — отрицательный код
и определение владельца. Для пути `Rows.Amount` дополнительно сохраняется реальное
определение табличной части. Проверяются вид элемента и вся цепочка владения;
неподдержанные более глубокие пути отклоняются.

Вложенный путь RLS реквизита табличной части имеет вид
`{{0, UUID табличной части}, {0, UUID реквизита}}`. Он подключён к общему
преобразованию `Rights.xml`, обратному разрешению имени и сбору XML-определений.
Связи включают табличную часть и её реквизит; защита удаления проверяет оба UUID.
Формат подтверждён независимой компиляцией справочника 8.5.1.1529. Тем же общим API
помещено изменение условия `ProbeRows.ProbeValue`, затем CF загружен Конфигуратором
и выгружен в совпадающий XML. В нативном описателе подтверждены четыре связи:
владелец, табличная часть, реквизит и корень; посторонние члены CF сохранились.
Алгоритм работает по карте владения; другие классы владельцев отдельно в этом
сценарии не проверены на сервере.

Номер строки табличной части пока не включён: проба права на
`TabularSection.ProbeRows.StandardAttribute.LineNumber` вызвала зависание нативного
импорта в тестовом Конфигураторе, остановленного по тайм-ауту. Ограничение с именем
реквизита относительно самой табличной части также не возвращается в нативную
XML-выгрузку; поддержан проверенный вариант относительно хранимого владельца.

`role_standard_attributes_851.json` содержит 61 стандартный реквизит девяти
классов: справочника, документа, журнала документов, плана обмена, плана видов
характеристик, регистра сведений, регистра накопления, задачи и бизнес-процесса.
Соответствия получены независимой компиляцией отдельных ролей 8.5.1.1529.
Заголовок стандартного `Catalog.Code` имеет вид
`{1, UUID справочника, 1, {-2, 03f171e8-326f-41c6-9fa5-932a0b12cddf}, 1}`.
UUID здесь обозначает общий класс стандартных полей, а конкретное поле определяется
отрицательным кодом и классом владельца: `Catalog.Code` — `-2`, `Catalog.Ref` — `-8`,
но `Document.Number` — тоже `-2`. UUID экземпляра стандартного реквизита не создаётся.

Для 59 стандартных полей подтверждены также пути RLS вида `{{0},{-2}}`.
У `AccumulationRegister.RecordType` и `DocumentJournal.Type` тестовый Конфигуратор
сохраняет введённую матрицу нативно, но не возвращает условие в XML-выгрузку;
поэтому их RLS пока явно отклоняется. Обычные права на эти два реквизита поддержаны.
Для предопределённых данных Конфигуратор объединяет ограничения `Predefined` и
`PredefinedDataName`: преобразователь сохраняет оба поля из целевого XML.
Порядок полей внутри одной строки сравнивается как набор; текст условия и порядок
самих строк сохраняются. Правила автоматического дополнения вручную написанного
XML не считаются полностью восстановленными.
На полном наборе из 1208 сохранённых ролей все 598 635 обычных заголовков
собраны заново через этот контекст без расхождений. 18 ссылок на уже отсутствующие
в XML элементы исключены из проверки. Новые стандартные правила проверены также
на независимой конфигурации 8.3.27.2342: все 189 020 стандартных заголовков собраны
обратно без расхождений, совпали 370 548 явно заданных состояний прав из XML.
18 ссылок на отсутствующих в XML владельцев исключены; ошибок сопоставления нет.
По совпадению
полных условий RLS независимо определены UUID `Read`, `Insert` и `Update`;
эти результаты согласуются с общим реестром прав.
Общая запись XML сохраняет буквальные CR через `&#13;`, чтобы повторное чтение
не превращало их в обычные переводы строк. Она используется при обратном XML-экспорте
метаданных, восстановлении исходного XML, автоматическом удалении и сборке
HTTP-запросов. Общие XML-инструменты не зависят от преобразователей оформления форм.

`role_right_identifiers_851.json` содержит однозначные UUID всех 69 имён прав,
встретившихся в исследованных выгрузках. `role_right_identifiers.right_id(name)`
возвращает UUID, `right_name(uuid)` выполняет обратное преобразование. Например,
`ThinClient` соответствует `3c00c6ee-844e-4620-85e4-671e72f114d9`,
`WebClient` — `bd33c881-192c-4ef7-a51d-b146e38c5078`.
Неизвестные имена и UUID отклоняются; это покрытие исследованного набора,
а не утверждение о полноте каталога прав всех версий платформы.

Для 23 ранее неоднозначных прав в отдельной базе Конфигуратора 8.5.1.1529
скомпилированы пары ролей с выключенным и включённым правом. У 20 пар изменился
один UUID; у трёх изменились также связанные записи, включая явные запреты.
Они различены по совместным ограничениям независимых XML/нативных наблюдений.
Для восстановления всех 69 соответствий в тестах сохранено 131 наблюдение
без имён исходных ролей и объектов. Сопоставление не зависит от порядка записей;
источники и SHA-256 исходных CF закреплены в реестре и тестовом наборе.
Повторный сбор наблюдений из сохранённой конфигурации 8.3.27.2342 достиг
однозначности после 866 ролей, без противоречий с прежними кандидатами.

На 23 независимых целых файлах Конфигуратора 8.5.1.1529 совпали заголовки,
состояния прав, флаги и шаблоны; порядок записей в таблице UUID не используется
для сопоставления. Учтены шесть явных запретов совместимости корня, которые
Конфигуратор может записывать в нативный поток без записей в XML.
На пяти нативных описателях из одноразовых тестовых хранилищ подтверждены связи
роли с корнем, справочником, внешним источником, непосредственным реквизитом
и полем ограничения RLS. Это реальные UUID элементов, а не только UUID их
хранимых владельцев. Проверка удаления учитывает сохранённые и заменённые
потоки прав; UUID самих прав и UUID внутри текста условий не становятся связями.

Общий OneScript-вход поместил изменение полного файла прав с условием на поле
в отдельное хранилище 8.5.1.1529. Конфигуратор загрузил полученный CF и выгрузил
правильное условие `WHERE TRUE` для `ProbeField`. Нативные CF версий до и после
помещения отличаются только потоком прав этой роли и служебным списком версий;
остальные члены контейнера сохранились побайтно.

Тем же общим входом создана новая роль с полным файлом прав: непосредственное
поле RLS, многострочный шаблон с кавычками и независимые права дочерних объектов.
Полученный CF также загружен Конфигуратором; XML-выгрузка сохранила объекты,
права, условия, шаблон и флаги. Добавились только описание роли и её поток,
из прежних членов контейнера изменились только корень и служебный список версий.
Проверка потоков новых объектов в OneScript читает `files` и `modules` из одного
профиля; суффикс, не объявленный в профиле, отклоняется.

Через тот же общий API проверены изменение права редактирования стандартного
`Catalog.Code` и изменение условия RLS для `Code`. Конфигуратор загрузил CF и
выгрузил полный ожидаемый XML обеих ролей. Нативные описатели до и после помещения
подтвердили связи только с владельцем и корнем; отрицательный код и UUID класса
стандартных полей не попали в зависимости. Между версиями тестового хранилища
изменились только два потока прав и служебный список версий.

Остаются стандартные реквизиты других классов, два неподтверждённых поля RLS,
номер строки табличной части, более глубокие пути полей, права за пределами реестра,
более широкая проверка классов и сочетаний условий на платформе.
Преобразуется экспортированный состав прав; полная система автоматических
включений зависимых прав для произвольного вручную написанного XML ещё не
восстановлена. Поддержка произвольной роли пока не заявляется.

### Формы и модули

Преобразователь читает **весь целевой `Form.xml`**, а не список изменений отдельных
элементов. Создание и изменение используют общие правила. Поддержаны поля ввода,
флажки, надписи, группы, страницы, кнопки, таблицы, картинки-декорации,
переключатели, индикаторы и календарные поля в пределах сопоставленных свойств.
Есть правила оформления, событий, команд, списков выбора и привязок к данным.
Обычные формы исключены из области поддержки и не планируются. Цель — полное
преобразование управляемых форм; текущее покрытие пока ограничено описанными правилами.

Операции создания и изменения собраны в `managed_form_operations.py`: `create`
создаёт форму и обновляет владельца, `change` проверяет текущую форму и заменяет
её потоки. Общий JSON-вход `serialize` требует явное поле `operation` со значением
`Создание` или `Изменение`. Преобразование интерфейса остаётся в
`managed_form_xml.py`, описания — в `form_definition_xml.py`. Для изменения
интерфейса передаётся полный `Form.xml`; замена только текста модуля сохраняет
интерфейс и всё равно формирует полный внешний поток формы. Ветка добавления
поля по `attribute_name` и её вспомогательный преобразователь удалены.

Реестр включает справочники, документы, журналы, перечисления, обработки и отчёты,
все четыре вида регистров, три вида планов (счетов, характеристик и расчёта),
планы обмена, бизнес-процессы, задачи, критерии отбора, хранилища настроек и
таблицы/кубы/таблицы измерений внешнего источника. Общие формы обрабатываются
тем же преобразователем. Внешние EPF/ERF не являются отдельными объектами
конфигурации в хранилище и не добавляются этим входом.

Для каждого владельца проверены создание и замена формы без основного реквизита:
скалярный реквизит строки, поле с привязкой к нему и полный модуль. Это подключение
всех классов владельцев, а не полное покрытие всех вариантов их форм. Основные
реквизиты справочников, документов, обработок, отчётов, планов счетов и видов характеристик, четырёх видов регистров
поддержаны в пределах профилей ниже. Динамические списки и несопоставленные
основные типы остальных владельцев пока отклоняются явно.

Основной `Object` плана видов характеристик использует XML-имя типа
`cfg:ChartOfCharacteristicTypesObject.<Имя>` и UUID из тела владельца. Подключены
код, наименование, пометка удаления, свои строковые, булевы, составные и ссылочные
реквизиты, `TypeSet`, табличные части и их колонки в пределах проверенного профиля.
Восемь форм у семи владельцев проверены общим помещением по HTTP и нативной
загрузкой CF: полные XML описаний и интерфейсов совпали, тела владельцев совпали
с независимыми нативными образцами. Отдельный вариант содержит нестандартные
имена таблицы и дополнений поиска; ссылки между ними и буквальный текст заголовка
сохранились. Режимы использования формы для папок пока не поддержаны.
Последующим общим пакетом изменены все восемь описаний, заголовки полей и полные
модули из `Ext/Form/Module.bsl`. После нативной загрузки XML совпали с независимой
компиляцией целевых файлов, тексты модулей сохранились, остальные члены CF
остались прежними.

При одинаковом XML нативный импорт и создание формы могут хранить значения по
умолчанию и идентификаторы вспомогательных элементов по-разному. Фикстура
`characteristic_forms_851.json` содержит оба проверенных варианта интерфейса:
исходный нативный и полученный после помещения и загрузки CF Конфигуратором.
Для создания сравнивается весь второй интерфейс без удаления полей, а его
полная XML-выгрузка отдельно сравнивается с целевым XML.

Добавление формы или макета к владельцу сохраняет потоки его встроенных команд
общей процедурой `inline_command_xml.preserve_owner_streams`. Принадлежность
проверяется по нативной коллекции команд, её профилю и карте признаков владельца;
посторонние UUID и неверные суффиксы потоков отклоняются. Тот же механизм
используется при изменении только позиции объекта. Общий план полной папки
передаёт в пересборку только изменённые файлы модулей владельца и команд;
неизменённые тексты и версии потоков сохраняются. Точная сохранность остальных
членов CF подтверждена при добавлении восьми форм.

Основной `Object` справочника, документа, обработки и отчёта можно сочетать с
дополнительными реквизитами: строкой, числом, булевым и датой, а также их
составными типами и ссылками на существующие справочники, документы и перечисления.
Коллекция реквизитов собирается целиком из `Form.xml`, включая порядок и удаление;
элементы могут одновременно ссылаться на поля объекта и дополнительные реквизиты.
Имя, положительный идентификатор и положение основного реквизита берутся из XML;
привязки его полей и табличных частей перестраиваются под выбранные имя и номер.
Ограничения на `Object`, идентификатор `1` и первое место в коллекции сняты.
Для справочника загрузка полученного CF и обратная
выгрузка в Конфигураторе 8.5.1.1529 подтвердили все четыре скалярных типа,
привязки элементов и полный текст модуля. Для документа смешанный состав также
проверен автоматическим тестом преобразователя.

Для регистров подключён общий сборщик основных реквизитов:

- Менеджер записи регистра сведений (`InformationRegisterRecordManager`).
- Наборы записей регистров сведений, накопления, бухгалтерии и расчёта
  (`…RecordSet`), включая привязку таблицы к набору и колонок к его полям.
- Измерения, ресурсы и реквизиты разрешаются из нативных групп владельца:
  используются реальные имена, UUID и типы полей. Для регистров накопления и
  бухгалтерии сопоставлены `Period`, `Recorder`, `LineNumber`, `Active`,
  для регистра расчёта — `Recorder`, `LineNumber`, `Active`.
- Для регистра сведений `Period` доступен у периодического регистра;
  `Recorder`, `LineNumber`, `Active` — при подчинении регистратору.
  Эти условия читаются из общей карты привязок. Остальные стандартные поля
  и режимы остальных видов регистров пока не подтверждены.

UUID основного типа берётся из сгенерированных типов текущего владельца;
запись и набор записей используют разные типы. Неизвестные типы, чужой владелец,
неверные группы и пути полей отклоняются. Основной реквизит можно сочетать с
дополнительными скалярными реквизитами по общим правилам.

Нативная проверка 8.5.1.1529 подтвердила пять форм: менеджер записи и набор записей
регистра сведений, по набору записей остальных трёх видов регистров. Проверены
измерения, ресурсы, реквизиты, перечисленные стандартные поля и основной реквизит
с именем `Data` и номером `17`. Собранные из шаблонов формы загружены в
Конфигуратор: полные XML интерфейсов и модули совпали с нативными образцами.
Через HTTP также проверены изменение четырёх существующих форм и создание новой
формы набора записей регистра сведений на текущем составе лабораторных регистров.
После чтения из хранилища подтверждены полные XML и модули; остальные тела,
потоки и требования к платформе сохранились побайтно.

Для регистра сведений отдельно проверены 13 сочетаний: независимый регистр
без периодичности и с периодичностью секунда, день, месяц, квартал, год;
подчинённый регистратору — те же варианты и позиция регистратора.
Из полных XML собраны 13 владельцев и 26 форм (менеджер записи и набор записей).
После загрузки CF в Конфигуратор 8.5.1.1529 полные XML владельцев и форм,
а также модули совпали с нативными образцами. Смена режима существующего
регистра с сохранением сгенерированных типов и дочерних коллекций покрыта
автоматическими тестами. Через HTTP также подтверждено совместное изменение
периодичности, добавление реквизита и преобразование форм в одном пакете.
Нестроковые реквизиты с пустым значением заполнения сериализуются как `U`.
Неизвестные значения режима и недоступные стандартные поля отклоняются.

Через `ПодготовитьКонфигурациюИзВыгрузки` проверено одно HTTP-помещение регистра
с переходом на периодичность «День», новым булевым реквизитом, изменённой формой
и новой формой. Обе формы привязаны к `Period` и новому реквизиту. Обратное чтение
версии и выгрузка Конфигуратора подтвердили владельца, описания форм, интерфейсы
и модули; посторонние нативные данные сохранились побайтно. При сравнении XML
учитываются нативная группировка дочерних коллекций и служебные пустые элементы,
которые платформа добавляет автоматически. Вторым HTTP-помещением без создания
и удаления объектов проверены переход на периодичность «Месяц», второй новый
реквизит и привязки к нему обеих существующих форм; обратная выгрузка подтвердила
тот же набор проверок. Связь подчинённого регистра с документом
задаётся отдельно в документе.

Дополнительно через HTTP проверены отказ до захвата и помещения при удалении
поля, используемого неизменёнными формами, и автоматическое включение двух
таких форм при замене UUID и смене типа поля с булева на дату. В целевой папке
редактировался только XML регистра. После помещения и нативной обратной выгрузки
подтверждены новое поле, привязки обеих форм, их полные интерфейсы и модули;
посторонние нативные данные сохранились побайтно.

Для дополнительных реквизитов поддержаны `cfg:CatalogRef`, `cfg:DocumentRef`
и `cfg:EnumRef`, в том числе несколько ссылочных типов вместе со скалярными.
UUID типа берётся из сгенерированных типов нативного объекта; UUID самого объекта
метаданных не используется вместо него. Общий план ссылок запрашивает нужные
снимки, а сборщик сверяет их версии и идентичность с контекстом хранилища.
Изменение формы также может разрешать типы из полного пакета версии.
Пропущенные снимки, неизвестные типы, неоднозначные имена и устаревшие версии
отклоняются. Правила доступны и общим формам, и формам со скалярными реквизитами
без основного `Object`.

Дополнительные реквизиты `v8:ValueTable` и `v8:ValueTree` используют общий
сборщик коллекций. Весь состав `Columns` берётся из целевого `Form.xml`: имена,
локальные идентификаторы, порядок, заголовки и типы колонок. Колонки поддерживают
те же скалярные, составные и ссылочные типы, что и другие дополнительные реквизиты;
снимки ссылочных типов запрашиваются и для колонок. Вложенные таблицы и деревья
внутри колонки и несопоставленные свойства явно отклоняются.
Поддержаны локализованные заголовки реквизитов и колонок, включая изменение
и очистку. Элементы `Table` привязываются к коллекциям, поля — к их колонкам;
ссылки на удалённые колонки, чужую коллекцию и несовместимые типы отклоняются.

В Конфигураторе 8.5.1.1529 проверены создание таблицы и дерева с 12 типизированными
колонками и последующее изменение: переименование коллекции и колонки, смена типа,
перестановка и удаление колонок, очистка колонок дерева и замена модуля. После
загрузки собранных CF и обратной выгрузки совпал весь `Form.xml` с нормализацией
назначаемых платформой идентификаторов вспомогательных элементов и опускаемых
пустых секций `Columns`/`ChildItems`. Исправлены привязки служебных элементов
поиска и состояния к номеру новой таблицы, а также чтение явных идентификаторов
контекстных меню и расширенных подсказок в ранее сохранённой форме.

Нативная проверка в 8.5.1.1529 подтвердила составной тип из четырёх скалярных
типов и ссылки на справочник, отдельную ссылку на справочник и объединение ссылок
на справочник, документ и перечисление. Описания реквизитов совпали с результатом
Конфигуратора; сформированный CF успешно загружен и выгружен обратно в XML,
с сохранением привязок и модуля.

Через общий API по HTTP в 8.5.1.1529 также проверены три сценария для формы
справочника без основного реквизита: добавление составных и ссылочных типов,
таблицы и дерева в существующую форму; повторное изменение имён, порядка и типов
колонок, их удаление и очистка дерева; создание отдельной новой формы с тем же
составом данных. При создании снимки трёх ссылочных объектов получены библиотекой
из текущего контекста. Каждый результат прочитан из хранилища, загружен в
Конфигуратор и выгружен обратно в XML: подтверждены интерфейс, реквизиты, колонки,
заголовки, привязки и полный модуль. Коллекция форм владельца обновлена корректно;
остальные тела объектов, потоки и требования к платформе сохранились побайтно.

При сравнении учитывается нормализация платформы: назначаемые идентификаторы
вспомогательных элементов, опускание пустых `Columns`/`ChildItems` и порядок типов
в составном описании. Состав типов и квалификаторы проверяются полностью;
порядок реквизитов, колонок и элементов интерфейса проверяется строго. UUID
ссылочных типов разрешаются заново для каждого контекста, без сохранённых
идентификаторов из другого хранилища.

Для завершения преобразователя управляемых форм остаются:

- Общая модель реквизитов: ссылки на другие классы метаданных,
  остальные квалификаторы и свойства
  реквизитов и колонок. Таблицы и деревья значений, составные типы из четырёх скалярных типов
  и ссылок на справочник, документ и перечисление уже поддержаны в пределах
  описанного выше профиля.
- Основные реквизиты остальных владельцев, полный состав стандартных полей
  и варианты режимов регистров. Разрешение типов и путей должно учитывать также
  одновременно создаваемые отдельно хранимые типы; поля изменяемого владельца
  уже разрешаются из его итогового тела в пакете полной папки.
- Динамические списки: описание типа, основная таблица или запрос, поля,
  настройки и привязки элементов формы.
- Несопоставленные свойства описания и интерфейса формы, параметры, варианты
  командной панели, свойства и события элементов. Уже известные виды элементов
  не означают поддержку всех их свойств; неизвестные конструкции отклоняются.
- Совмещённые изменения: типы реквизитов от новых отдельно хранимых объектов,
  назначения форм вместе с остальными свойствами и модулями владельцев
  без полного XML-профиля;
  зависимости, не описанные путями
  основного реквизита (в том числе команды и динамические списки). После расширения
  правил нужны сравнения полных форм из реальной конфигурации с нативным результатом,
  включая сохранность интерфейса и текста модуля.

Изменение списка и назначений форм не требует полного сериализатора владельца:
редактор меняет его нативные коллекции и сопоставленные поля ссылок, сохраняя
остальные байты и версии потоков.
Для владельцев без полного XML-профиля исходный XML берётся из исходной полной
папки; остальные свойства должны совпадать. В одиночном входе для такого владельца
нужен `ПутьИсходногоXML`. Изменение свойств неподдерживаемого владельца отклоняется.

Для формы автоматически ищется соседний `Ext/Form/Module.bsl`. При наличии файла
берётся весь его текст; изменение только модуля также поддерживается. Отсутствующий
файл при изменении сохраняет существующий модуль, пустой файл очищает его текст.
Для поддерживаемых объектов модули читаются из их папки `Ext` по реестру профилей.

### Макеты

XML-описание макета задаёт его UUID, свойства и вид; содержимое читается рядом:

| Вид макета | Файл содержимого | Преобразование |
| --- | --- | --- |
| `DataCompositionSchema` | `<Макет>/Ext/Template.xml` | Полная СКД, включая поддерживаемые варианты настроек, макеты и оформление; ссылки разрешаются по контексту хранилища |
| `BinaryData` | `<Макет>/Ext/Template.bin` | Двоичные данные сохраняются побайтно |
| `TextDocument` | `<Макет>/Ext/Template.txt` | UTF-8, с сохранением BOM и переносов строк |

Основная СКД отчёта может назначаться ссылкой на его существующий макет.
Табличные документы, HTML и другие виды макетов предстоит подключить.
Для СКД остаются ограничения на несопоставленные типы, картинки и оформление.

### Удаление и связанные объекты

При обычном изменении через `ПодготовитьПакетИзВыгрузки` состав `ChildObjects`
считается полным целевым составом детей владельца. Если существующей формы,
макета или объекта верхнего уровня больше нет в XML, библиотека автоматически
включает его удаление и удаление всех его отдельно хранимых потомков в пакет.
Например, отсутствие справочника в `Configuration.xml` удаляет справочник вместе
с его формами и макетами. Отсутствие формы в XML справочника удаляет эту форму.

Передавать UUID удаления или отдельный признак полноты не требуется. Если у
владельца есть дети, отсутствие самой секции `ChildObjects` отклоняется; пустая
секция означает пустой целевой состав. Новые отдельно хранимые дети требуют своих
файлов и пакетов создания; их нельзя добавить одним именем при изменении владельца.
Неявное изменение порядка существующих детей также отклоняется.

Поддерживаемые изменения свойств владельца и удаления помещаются одновременно.
Встроенные реквизиты и табличные части по-прежнему преобразуются целиком из XML
владельца. Удаляемое содержимое отдельно хранимых объектов не требуется
пересобирать из XML, поэтому удаление не зависит от наличия преобразователя
создания для этого класса. Класс должен быть известен справочнику, а нативная
коллекция владельца — соответствовать проверяемой структуре.

Общий редактор отдельно хранимых коллекций использует карту метаданных: путь или
поиск по UUID класса, счётчик и список UUID детей. Перед изменением он сверяет
класс и UUID владельца, состав детей, их родителей, порядок и позиции с актуальным
снимком. Неизвестные и неоднозначные структуры отклоняются. Для корня редактор
заменяет только изменённые участки коллекций, сохраняя остальные байты тела.
Встроенные коллекции продолжают обрабатываться преобразователями полного XML.

Автоматическое удаление форм подключено для всех 21 вида владельцев из реестра;
общие формы удаляются из коллекции конфигурации. Создание, изменение и удаление
форм проверены для каждого вида владельца. Остальные коллекции доступны в пределах
сопоставленных правил карты; это не означает поддержку всех дочерних коллекций
метаданных. Допустимые родители удаления в Python и OneScript определяются одной
картой. Явный метод удаления одного объекта использует эти же правила.
Он использует тот же сборщик, но требует сохранить остальные свойства, встроенные
коллекции и потоки владельца. Для совмещения удаления с изменениями свойств
используется общий вход по целевому XML владельца.

Удаление работает в профиле `legacy`. Корень конфигурации удалять нельзя.
При автоматическом удалении несколько объектов и их потомки удаляются одним
пакетом. Прямой метод `ПодготовитьУдалениеОбъекта` сохраняет режим удаления одного
объекта без детей; для каскада следует передать целевой XML его владельца общему входу.
Входящие ссылки из графа хранилища, включая ссылки на встроенные идентификаторы,
и выбранные формы/макеты владельца также блокируют удаление. Механизм не анализирует
семантику произвольного BSL-кода и не заменяет проверку конфигурации платформой.
Для XML владельца сохраняются ограничения его проверенного профиля свойств.

Подготовка и помещение доступны как через общий вход, так и явно:

```bsl
Объект = Клиент.ПолучитьОписаниеОбъекта(UUIDОбъекта);
Пакет = Клиент.ПодготовитьУдалениеОбъекта(
    Объект, "C:\Export\Configuration.xml", "python");
// Захватить все Пакет.СуществующиеОбъекты: владельца и удаляемый объект.
Родитель = Клиент.ПоместитьУдалениеОбъекта(Пакет, "Удаление объекта");
Клиент.ОтменитьЗахватОбъекта(Родитель);
```

`ПодготовитьУдалениеФормы` и `ПоместитьУдалениеФормы` сохранены как совместимые
входы в тот же механизм. Пакет хранит удаляемое описание в `УдаляемыйОбъект`;
прежнее поле `Форма` остаётся совместимым алиасом. Полный список находится в
`УдаляемыеОбъекты`. Захватить нужно все `СуществующиеОбъекты`, включая потомков.
Удаляются также внешние потоки объекта. Потоки владельца сохраняются либо
заменяются целиком, если в целевой выгрузке переданы поддерживаемые файлы модулей.

Перемещение между владельцами ещё не реализовано. Встроенные поля и значения перечисления удаляются
через полный XML содержащего их объекта, а не как отдельные объекты хранилища.

Пакет может включать новый объект, изменения владельца и связанные объекты.
Для регистра накопления или бухгалтерии документы-регистраторы передаются через
`СвязанныеXML`. Автоматического сравнения всей папки выгрузки и построения пакета
любого набора изменений пока нет.

## Общий порядок работы

1. Подключиться к хранилищу и подготовить полные целевые файлы выгрузки.
2. Вызвать `ПодготовитьПакетИзВыгрузки(ПутьXML, Настройки, ПутьPython)`.
3. Захватить необходимые существующие объекты из `Пакет.СуществующиеОбъекты`.
4. Отправить пакет через `ПоместитьПакет` и освободить оставшиеся свои захваты,
   используя актуальные описания объектов.

Подготовка сама не выполняет захват или помещение. Она получает свежий контекст
хранилища и проверяет исходные версии; при изменении хранилища пакет нужно
подготовить заново. После неоднозначного ответа помещения сначала следует
проверить состояние сервера, поскольку версия могла уже сохраниться.

```bsl
Клиент = Новый КлиентХранилища(
    "http://localhost/repo/repo.1ccr", "8.5.1.1529");
Клиент.Подключиться("Пользователь", "Пароль", "Хранилище");
Пакет = Клиент.ПодготовитьПакетИзВыгрузки(
    "C:\Export\CommonModules\ОбщийМодуль.xml", Неопределено, "python");
Для Каждого Объект Из Пакет.СуществующиеОбъекты Цикл
    Клиент.ЗахватитьОбъект(Объект);
КонецЦикла;
Результат = Клиент.ПоместитьПакет(Пакет, "Изменение общего модуля");
```

Настройки общего входа:

- `Операция`: `Авто` по умолчанию, `Создание`, `Изменение`, `Удаление`.
- `ИдентификаторРодителя`: UUID владельца нового дочернего объекта, если путь
  не соответствует структуре выгрузки.
- `СвязанныеXML`: массив полных целевых XML связанных документов.
- `ИдентификаторОбъекта`: UUID явно удаляемого отдельно хранимого объекта.
- `ПутьИсходногоXML`: дополнительный исходный XML корня для сценариев проверки
  свойств вне самостоятельного поддерживаемого профиля; не расширяет покрытие.

При `Авто` создание или изменение выбирается по наличию UUID в хранилище.
При изменении полный XML владельца автоматически определяет удаления его детей.
`Операция = "Удаление"` с `ИдентификаторОбъекта` остаётся отдельным явным входом.

## Устройство и проверка

OneScript отвечает за HTTP API и подготовку контекста. Python читает XML и
сопутствующие файлы, применяет правила сопоставления и строит пакет. `v8unpack`
собирает нативные структуры из подготовленной модели; он не читает XML
Конфигуратора напрямую и не заменяет правила сопоставления.

Общий сборщик пакетов формирует граф, версии, внешние потоки и транспортный
контейнер. Поддерживаемые свойства берутся из полного целевого файла; неизменяемые
структуры и потоки сохраняются из актуального снимка. Это ещё не полностью
самостоятельное восстановление любого объекта только по XML.

Есть автоматические проверки преобразований, пакетов и отказов на неподдерживаемых
структурах. Основные сценарии проверялись помещением в хранилище 8.5.1.1529,
нативной загрузкой CF и сравнением XML/потоков с результатом Конфигуратора.
Такая проверка подтверждает конкретные сценарии, а не всё содержимое класса.
Общее удаление проверено на сервере для общего модуля с внешним текстом:
после создания и удаления нативная загрузка и сравнение выгрузки подтверждают
восстановление исходного состава. Также проверены автоматическое удаление одной
формы вместе с изменением комментария справочника и последующее одновременное
удаление справочника, оставшейся формы и общего модуля по `Configuration.xml`.
Нативная загрузка подтверждает удаление объектов и потоков, восстановление
исходного XML и сохранение остальных файлов контейнера. Удаление форм и макетов использует тот же
пакет и сохраняет ранее проверенные сценарии. Другие классы удаления проверяются
автотестами структуры пакета; отдельная серверная проверка каждого класса не проведена.
Для общего редактора дополнительно проверено удаление одной из двух форм регистра
сведений вместе с изменением комментария владельца. Нативная загрузка и XML
совпали с результатом Конфигуратора; вторая форма, макет и остальные файлы сохранились.
Два неизменённых участка нативного тела оставлены в исходном представлении:
полная пересборка XML Конфигуратором нормализует их кодирование без изменения XML.
Явным методом также проверено удаление макета этого регистра: после нативной
загрузки изменилась только коллекция макетов, его внешние потоки исчезли,
а оставшаяся форма и остальные файлы контейнера сохранились.
Групповое помещение проверено одновременным изменением комментариев корня и
регистра сведений: сервер создал одну версию, нативная загрузка CF и сравнение XML
подтвердили оба изменения и сохранение остальных файлов. В автотестах проверяются
также несколько внешних потоков, дедупликация одинакового содержимого,
несогласованные версии и отказ при попытке смешать разные операции.
Обход полной папки также проверен на сервере: отобраны только два изменённых
описания, неизменённые объекты пропущены, создана одна версия. Нативная загрузка CF
и сравнение всей выгрузки подтвердили целевой состав и содержимое, повторное
использование устаревшей исходной выгрузки отклонено.
Смешанное помещение также проверено на сервере: изменения корня и регистра
сведений и удаление его формы создали одну версию. Нативная загрузка CF и сравнение
всей выгрузки подтвердили целевой состав, исчезновение формы и её внешнего потока
и сохранение остальных файлов. Проверки входящих ссылок выполняются перед сборкой
конечного пакета; поддержка ссылок и содержимого по-прежнему ограничена профилями
соответствующих преобразователей.
Создание, изменение и удаление в одной версии проверены на константах: созданы
два объекта, изменён корень, удалён старый объект и обновлена позиция оставшегося.
Нативная загрузка CF на 8.5.1 и XML-выгрузка подтверждают результат; заголовок
совместимости и неизменённые тела сохранились. Экспериментальный UUID
`ConstantCollectionChanged` в профиле `legacy` не отправляется как требуемая
возможность платформы, поскольку это делает CF несовместимым с проверенной сборкой.
Общие формы и новые формы существующего справочника проверены в общем пакете
полной конфигурации: одновременное создание двух форм с модулями, изменение
владельца и удаление общей формы приняли сервер и Конфигуратор 8.5.1. Нативная
XML-выгрузка подтверждает поля и привязки к коду/наименованию, полные тексты
модулей и отсутствие удалённой формы. Неизменённые тела констант, оставшейся
общей формы и её модуль сохранились; заголовок совместимости CF не изменился.
Массовая нативная проверка также выполнена для всех 21 вида владельцев:
созданы новые формы и заменены существующие с полным интерфейсом и модулем.
Общие пакеты приняли изолированные хранилища, а загрузка CF и повторная XML-выгрузка
подтвердили скалярные поля, привязки, модули и неизменённую совместимость.
Удаление форм также проверено для всех 21 вида владельцев. Оставшиеся формы
сохранили тела и модули, их позиции уплотнились, удалённые формы и внешние потоки
исчезли. Снимки объектов, у которых меняется только позиция, входят в общий план
даже при отсутствии новых объектов. Соответствие XML-имён и внутренних имён
классов учитывается, включая планы видов характеристик.
Для двоичных и текстовых макетов нативное создание и изменение проверены на общих
макетах; макеты владельцев подключены к тому же механизму, но не все сочетания
видов и владельцев отдельно проверены на сервере.

Алгоритм нативного идентификатора версии полностью не восстановлен: используемый
UUID + CRC32 остаётся экспериментальным. Универсальная совместимость с платформой
и промышленная готовность всех преобразователей пока не подтверждены.

## Что предстоит сделать

1. Завершить сопоставление свойств, типов, ссылок и сопутствующих файлов уже
   подключённых классов. Расширить формы и виды макетов.
2. Расширить неполные профили классов: общих команд и реквизитов, функциональных
   опций, планов обмена, планов видов характеристик и расчёта, регистров расчёта,
   задач и бизнес-процессов. Завершить права ролей и остальные отсутствующие правила;
   расширить проверку XDTO-типов и импортов платформой. Точное покрытие каждого
   подключённого класса и его ограничения приведены выше.
3. Расширить переименование с сохранением UUID на оставшиеся классы и сочетания зависимостей.
   Смена владельца формы рассматривается как удаление прежней формы и создание
   новой с новым UUID, с изменением коллекций обоих владельцев; отдельная операция
   перемещения формы не требуется. Расширить проверку одновременных созданий и
   удалений в одном целевом XML владельца и между владельцами.
   Сквозной автоматический тест проверяет замену формы регистра общей формой:
   новый UUID, копирование полного интерфейса и модуля, изменение коллекций обоих
   владельцев, удаление старой формы и единственную сборку пакета. Этот сценарий
   пока проверен без отправки серверу; он не доказывает перенос формы с главным
   реквизитом между двумя прикладными объектами.
   Независимый импорт XML в отдельную базу Конфигуратором 8.5.1.1529 также
   подтвердил удаление формы справочника и создание формы документа с новым UUID:
   интерфейс и модуль сохранились, DefaultObjectForm документа обновился,
   старый UUID отсутствует в конечном CF. Та же замена проверена через общий
   HTTP-вход в отдельном хранилище: версия принята, тела обоих владельцев и новой
   формы, вся XML-выгрузка совпали с независимой нативной сборкой; посторонние члены
   CF сохранились побайтно. Дополнительно через HTTP проверена обратная замена
   формы документа с главным реквизитом формой справочника: новый UUID формы,
   новый UUID основного типа и путь Object.Code; полная выгрузка совпала с
   независимой нативной сборкой. Другие сочетания владельцев и привязок ещё
   требуют расширения проверок.
4. Расширить общий граф на остальные вложенные создания и зависимости между
   новыми объектами, оптимизировать чтение исходных снимков; убрать необходимость
   исходной папки после расширения
   обратного преобразования нативных снимков в XML.
5. Восстановить алгоритм нативных версий, исправить получение истории версий и
   расширить проверки совместимости за пределы основной сборки 8.5.1.1529.

Критерий завершения — возможность поместить произвольный поддерживаемый платформой
набор изменений конфигурации без ручного формирования нативных пакетов и потери
свойств. Текущее покрытие до этого критерия ещё не дошло.

Переименование подключено к `ПодготовитьКонфигурациюИзВыгрузки` для объектов,
проходящих через `object_change_serializer` и общий
`metadata_object_xml.change(..., allow_rename=True)`, а также к обработчикам
общих модулей, управляемых форм, макетов и общих макетов поддержанных видов;
отдельный вход подготовки одного объекта по-прежнему его отклоняет. Преобразователь
поддерживает изменение имени в теле с сохранением UUID объекта и сгенерированных
типов. Независимый импорт в Конфигуратор 8.5.1.1529 подтвердил три образца
справочника: обычный, иерархический и с числовым кодом. В каждом нативном теле
изменилось только имя; преобразователь воспроизвёл тело целиком. Фикстура:
`tests/fixtures/metadata_rename_851.json`, проверки: `tests/test_metadata_rename.py`.
Общий вход сопоставляет определения и сопутствующие файлы по UUID и относительному
пути внутри объекта: перенос папки из-за нового имени не очищает модуль и не
создаёт лишние изменения неизменённых детей. Класс и владелец существующего UUID
должны совпадать. Конечный индекс использует новое имя, а чтение исходных типов
проверяет прежнее имя, UUID и версии по исходным снимкам. Описание помещаемого
объекта получает новое имя; групповая проверка OneScript разрешает эту разницу
только для входа полной конфигурации. По HTTP в отдельном хранилище проверено
переименование всех трёх справочников одной версией. Нативная загрузка результата
и XML-выгрузка подтвердили новые имена и пути; тела совпали с независимыми
нативными образцами, остальные члены CF сохранились.
Повторное переименование тех же трёх справочников принято следующей версией;
нативная загрузка, сравнение полных тел и XML подтвердили изменение только имён,
включая сохранение всех остальных членов CF.
Дополнительно проверено единое помещение 18 переименований: десяти общих модулей
с разными флагами и режимами повторного использования значений, общей и
подчинённой формы, общих и подчинённых макетов двоичных данных, текстового
документа и СКД. Конфигуратор загрузил CF; полные тела определений совпали с
независимой нативной компиляцией. В телах изменились только имена, UUID и все
внешние члены CF сохранились. Нативные образцы находятся в
`tests/fixtures/definition_rename_851.json`, проверки — в
`tests/test_definition_rename.py`.

Следующим общим пакетом эти 18 объектов переименованы обратно с одновременным
изменением текстов общих модулей, интерфейсов и модулей форм, двоичных и текстовых
макетов. Полные тела, XML и файлы после нативной загрузки совпали с отдельной
компиляцией целевой выгрузки. Неизменённые потоки двух макетов СКД и остальные
члены CF сохранились побайтно.

Если меняется только описание, общий `native_content.body_change` сохраняет
интерфейс формы, текст модуля и содержимое макета вместе с версиями потоков.
Это позволяет переименовать форму без преобразования её неизменённого интерфейса.
При изменении привязок владельца этот путь отключается: даже неизменённый XML
интерфейса пересобирается с новыми UUID полей. Если содержимое действительно
изменено, работают прежние преобразователи целых файлов.

Переименование самой конфигурации проверено отдельным помещением одного корня
без изменения остальных объектов. Нативная загрузка и полная XML-выгрузка
подтвердили новое имя; UUID корня и встроенных признаков сохранились. В теле
корня заменён только токен имени, включая сохранение непреобразованных служебных
полей; остальные члены CF сохранились побайтно. Независимый контроль показал,
что XML-импорт платформы меняет одно служебное поле даже при неизменённом имени:
при помещении это поле сохраняется из текущего снимка.
Образец принятого корня и полного XML находится в
`tests/fixtures/configuration_root_rename_851.json`, проверки — в
`tests/test_configuration_root_rename.py`. Имя проверяется общей процедурой
`metadata_common_xml.name_value`; одиночный вход изменения корня сохраняет
прежний запрет переименования.

Переименование непрозрачных владельцев, текстовые ссылки в коде
модулей и все сочетания зависимых объектов этой проверкой не покрыты.

## Карта классов и дочерних коллекций

Полная карта XML формата 2.21 находится в `src/Сериализация/metadata_structure_221.json`: 75 классов и 173 дочерние коллекции. Она извлечена из XSD платформы и дополнена текущими нативными профилями. Это полнота схемы данного формата, а не обещание поддержки всех версий платформы или всего содержимого форм.

Для каждой коллекции записаны XML-имя и тип элемента, способ хранения, кратность, UUID класса или коллекции (если известен), путь в нативном теле, преобразователь и статус покрытия. Свойства класса, модули и поддерживаемые файлы содержимого также перечислены. UUID реквизита или формы является UUID экземпляра, а не UUID коллекции.

`stored_name` означает ссылку по имени на отдельно хранимый объект. `inline_xml` означает структуру внутри XML и нативного тела владельца; встроенный объект может при этом иметь собственный внешний поток, например модуль команды. Родитель и встроенный элемент сериализуются вместе. У формы XML-описание и содержимое `Form.xml` являются разными уровнями.

Статусы нативного преобразования: `verified_profile` — правило присутствует в проверенном профиле; `snapshot_collection` — коллекция находится по UUID класса в актуальном снимке; `unmapped` — допустимая XML-коллекция известна, но правило записи ещё не реализовано. Поддержка коллекции не означает поддержку всех свойств её элементов. Позиции и UUID относятся к профилю 8.5.1.1529. Карта также содержит путь проверки UUID владельца; дополнительные правила редактора и основания их проверки находятся в `collection_editor_profiles_851.json`.

Для некоторых ещё не подключённых коллекций записан `candidate_path`: позиция найдена в нативном шаблоне, но обработчик записи не реализован. Это подсказка для разработки, которая не активирует сериализацию. Вложенные реквизиты табличной части дополнены `owner_native_profiles`, поскольку правило зависит от владельца табличной части.

Схема показывает, например, вложенные подсистемы, формы и макеты регистров, флаги учёта плана счетов, методы HTTP-сервиса и поля таблиц внешнего источника данных. Их существование не активирует сериализацию автоматически: новые нативные правила сначала нужно добавить и проверить. Список родителей автоматического удаления теперь читается из карты, а поддержка вычисляется из реализованных обработчиков и профилей.

Карта пересобирается инструментом `tools/build_metadata_structure.py` из внешнего файла XSD. Источник закреплён коммитом, SHA-256 исходной схемы сохранён в JSON; во время работы библиотеки сеть и исходный XSD не требуются. UUID без проверенного профиля из справочника v8unpack помечены отдельным источником. Полный исходный XSD не включён в пакет.
