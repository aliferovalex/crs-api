# Возможности и ограничения CRS API

Состояние на 11 ноября 2026 года. Проверенная платформа — **8.5.1.1529**,
внешний компилятор — **ibcmd-rs 0.4.1**.

Цель проекта — помещение любого валидного изменения конфигурации. Допустимость
изменения определяется платформой 1С. Оставшиеся отказы компилятора и ограничения
читателей CRS рассматриваются как пробелы поддержки, в том числе для корректных
выгрузок. Ниже отдельно указано подтверждённое поведение и оставшиеся ограничения.

## Просмотр изменений без выгрузки конфигурации

`Клиент.ПолучитьИзмененияВерсии(НомерВерсии, ПолучатьСодержимое, ПутьPython)`
возвращает создания, изменения и удаления объектов любых классов. По умолчанию
`ПолучатьСодержимое=Истина`: метод сам находит предыдущую версию каждого UUID,
адресно получает полные исторические снимки до/после и сравнивает их. При
`Ложь` читаются только история и описания; Python для этого режима не нужен.
Захваты, запись в хранилище, полный CF и Конфигуратор не используются.
На длинной истории поиск предыдущего состояния может потребовать много
запросов `versionObjects`; это пока не индексируется в локальном кэше.

Результат — массив с полями `Идентификатор`, `Действие` (Создание, Изменение,
Удаление), описания `До`/`После`, `Свойства` (Свойство/До/После: имя, класс,
позиция, родитель, владелец), `СодержимоеПолучено`. При получении содержимого
добавляется `Содержимое`: `streams` только для отличающихся тел/потоков,
значения `before`/`after`, SHA-256, размеры, распакованные данные в Base64 и
текстовый `diff`, когда данные — UTF-8. `$body` обозначает тело объекта.
Нулевое число отличий допустимо: версия описания могла измениться без
изменения тела/потоков. Неизвестные двоичные потоки сохраняются без потери
данных. Для текста свыше суммарных 512 КиБ diff пропускается с `diff_omitted`,
сами данные сохраняются. Восстановление ранее удалённого UUID — Создание.

```bsl
Изменения = Клиент.ПолучитьИзмененияВерсии(10, Истина, "python");
// Быстрый состав помещения без загрузки тел и без Python:
Описания = Клиент.ПолучитьИзмененияВерсии(10, Ложь);
```

`Клиент.ПолучитьИсторическийОбъект(Объект, ПутьPython)` принимает историческое
описание из `СписокОбъектовВерсии`. Номер снимка — `Объект.НомерВерсии`, а
`Снимок.ВерсияХранилища` — текущий UUID хранилища, использованный в запросе.
Метод сначала получает тело и карту потоков, затем запрашивает все внешние
потоки с их историческими версиями. Проверяются UUID, класс, номер и
собственный номер версии, original/local, целостность и полнота потоков.
Неполный ответ или несовпадение — ошибка; подмена актуальным содержимым и
запасная полная выгрузка не допускаются. Описание с `Удален=Истина` не имеет
тела: для удаления используется последний существовавший снимок.

`СериализаторОбъектаХранилища.СравнитьСнимкиОбъекта(UUID, До, После, ПутьPython)`
также позволяет отдельно сравнить уже сохранённые снимки без сети.
`Неопределено` на одной стороне означает создание/удаление.

Для читаемого представления передайте четвёртым аргументом путь к ibcmd-rs:

```bsl
Изменения = Клиент.ПолучитьИзмененияВерсии(
    10, Истина, "python", "C:\tools\ibcmd-rs.exe");
```

В каждом элементе добавляется `Представление`. При `status=available` поле
`files` содержит XML/BSL/двоичные файлы с путём, действием, значениями до/после
и текстовым diff; для XML — `properties` с путями и значениями before/after.
Элементы формы сопоставляются по uuid/id/name, когда эти атрибуты доступны;
для остальных узлов используются позиционные индексы. Это сравнение XML,
а не отдельные правила для каждого свойства формы. BSL берётся из файлов,
созданных ibcmd-rs, без нативной оболочки потока. Двоичные данные сохраняются
с размерами и SHA-256. При `status=unavailable` возвращаются сторона и причина,
нативное `Содержимое` остаётся доступно; недоступность не означает отсутствие
изменений.

Преобразование использует `ibcmd-rs objects export --rows-dir --object` и
предварительный `mssql-dump-config --object` для проверки отчёта о покрытии.
Контекст собирается по нативным телам и карте коллекций: выбранный объект,
его предки и собственное поддерево, а также структурные UUID-ссылки на другие
объекты, существовавшие на выбранный момент. UUID из строковых литералов и
комментариев не считаются ссылками. Для каждого кандидата сначала читается
только историческое описание; тело запрашивается лишь для найденного объекта.
Версии, планы контекста, описания и снимки повторно используются внутри вызова.
Списки отдельно хранимых детей читаются из тела объекта: служебный список
детей снимка может быть пустым даже при наличии форм в справочнике.

Корень не разворачивается во всю конфигурацию. Для его дочерних коллекций
достаточно исторических имён, класса и родителя из описаний. ibcmd-rs
преобразует свойства и активы; затем общий редактор XML восстанавливает
именованные дочерние коллекции по проверенным UUID из тела и историческим
именам. Преобразованные свойства, inline-дети и привязки пространств имён
сохраняются. Неизвестное имя, противоречие класса/родителя или конфликт со
списком ibcmd-rs блокирует результат вместо выдачи неполного XML. Нативные
свойства не сериализуются этим механизмом и не меняются.

Полный CF не загружается и не собирается. ibcmd-rs не запускает SQL-запросы
в режиме `--rows-dir`. Неполные assets, непреобразованный UUID и свойства,
отмеченные компилятором как opaque, блокируют читаемый результат. Остаются
ограничения декодирования ibcmd-rs. Ссылки через генерируемые UUID типов и
непрозрачные внешние активы не образуют универсальный решатель зависимостей;
не все классы метаданных проверены в читаемом режиме.

На локальном TCP-сервере 8.5.1.1529 подтверждены разные тела корня версий
3, 5 и 21 (по одному объекту в пакете), исторические внешние потоки общего
модуля версий 9, 10, 20 и формы версий 11, 16. Через общий вход проверены
создание и изменения модуля/формы; с ibcmd-rs — обычный diff Module.bsl,
XML-изменения формы и создание константы. В отдельном ранее созданном
хранилище проверено получение и читаемый diff удаления формы, уже
отсутствующей в актуальном состоянии. Никакие изменения в эти хранилища
при проверке не вносились; UUID версии до и после совпал.

Два первоначальных случая `unavailable` устранены в сборке контекста:
корню не хватало записи основного языка, справочнику — форм из фактических
коллекций тела. Исправлять ibcmd-rs для этих случаев не потребовалось. Для
корня версии 21 все свойства и списки детей совпали с полным локальным
экспортом идентичного тела. Сетевая проверка общего входа показала ровно три
запроса снимков: корень версий 13 и 21 и язык версии 9; около 12 КБ ответов
снимков. Тела остальных объектов не читались, `devObjectsVersionEx` не вызывался.
История и описания версий по-прежнему читаются отдельно.

Для справочника до и после удаления формы свойства и дети также совпали с
полными локальными CF с идентичными телами: контекст составил 6 и 5 снимков
соответственно (корень, язык, справочник и его 3/2 формы). Эти проверки
выполнены без помещения новых изменений. Имена детей определяются на
исторический момент, включая переименованные и уже удалённые объекты.
Без пути ibcmd-rs метод возвращает прежнее нативное сравнение и требует только
Python для разбора снимков.

В `DevDepot_updateObjects/requested` сохраняются `verNum=-1`, `selfVerNum=0`
и нулевая локальная версия. Исторический снимок выбирается полным описанием
в `changes/value/second/_super`; внешние потоки — их историческими `verID`.
`clientVerID` — текущий UUID версии хранилища. В старой записи Конфигуратора
получение версии через `DevDepot_devObjectsVersionEx` возвращало CF целиком;
адресный механизм подтверждён отдельным экспериментом с сервером.

Автотесты проверяют состав помещения и предыдущую версию объекта, сравнение
тел/текстов/двоичных и пустых потоков, работу OneScript–Python, исторические
`verID` внешних потоков, отказ при несовпадении хешей и неполном ответе.

## Архитектура

Всё преобразование XML Конфигуратора в нативное содержимое выполняет
[ibcmd-rs](https://github.com/Untru/ibcmd-rs). Собственные XML-сериализаторы
объектов, форм, модулей, макетов и прав удалены. Запасного Python-преобразователя
нет. Если оба пути компиляции ibcmd-rs отклоняют ввод, подготовка прекращается.

CRS API отвечает за HTTP/TCP-протокол хранилища, авторизацию, получение и захваты,
снимки и версии объектов, граф зависимостей, описатели и итоговый пакет помещения.
Нативные читатели проверяют CF, UUID, типы, возможности и привязки форм.
Они не формируют нативные свойства из XML. Контейнеры CF Format15/Format16
читает и записывает встроенный `cf_container` (адаптированная часть v8unpack
1.2.13 с сохранением MIT-уведомления в `src/Сериализация/V8UNPACK-LICENSE.txt`).
Служебный нативный текст формирует `native_metadata`. Установка v8unpack и
других Python-пакетов не требуется. Конфигуратор при подготовке не запускается. Связи и примеры — в [карте модулей](module-map.md).

## Единый исполнитель помещения

Все виды пакетов отправляются через `Клиент.ПоместитьПакет(Пакет, Комментарий,
ИдентификаторПодключения)`: изменение, создание, удаление и смешанная группа.
Подготовка XML с захватом вызывает этот же вход. Старые методы
`ПоместитьОбъект`, `ПоместитьУдалениеОбъекта` и отдельные исполнители создания
и группы удалены. В менеджере запросов оставлен один построитель
`ТелоЗапросаНаПомещениеПакета`; обёртки «создание объекта/константы» удалены.

До отправки проверяются структура пакета, хранилище/платформа, версии и
исходные хеши всех исходных объектов, собственные захваты и отсутствие новых
UUID. Описания читаются согласованным пакетным запросом; перед единственным
`DevDepot_commitObjects` ещё раз сверяется версия хранилища. После ответа
для каждого объекта проверяются продвижение номера версии, ожидаемые имя,
позиция, класс, родитель, владелец и UUID локальной версии (первые 16 байт
контрольной суммы, поскольку сервер обнуляет последние 4 байта). Все
помещённые объекты должны принадлежать одному номеру версии; все удалённые
UUID должны отсутствовать. Эти проверки теперь одинаковы для одиночных
и групповых пакетов.

Групповой пакет возвращает массив описаний. Одиночное изменение/создание —
описание целевого объекта, удаление — описание обновлённого родителя.
Обновление основы выполняется после подтверждения результата, если пакет
содержит соответствующий контекст. Транспортные ошибки и ошибки подтверждения
не приводят к повторной отправке. Составная подготовка сохраняет неизвестный
исход в журнале; её проверки reviseDate и правила освобождения только
собственных захватов сохранены.

Синтетические TCP-тесты покрывают четыре вида пакетов, предусловия без отправки,
коллизию UUID одиночного создания, несовпадения всех подтверждаемых полей,
разные номера версий, неполное удаление и потерю ответа без повторного RPC.
Выявлена и исправлена недоступность межмодульной проверки XML описаний:
`ОбработкаXML.ПроверитьОтветОписанияОбъекта` теперь экспортирована для
пакетного чтения, которое её вызывает.

На отдельной копии тестового хранилища 8.5.1.1529 общий вход прошёл сквозную
цепочку XML → ibcmd-rs → захват → помещение → обновление основы: изменение
модуля, создание константы и её удаление (версии 24, 25, 26). На каждом шаге
основа продвинулась и исходный состав захватов сохранился. После удаления
состав объектов восстановлен, остальные записи приложения совпали побайтно
с состоянием после изменения модуля (кроме изменявшегося корня и служебных
записей). Хеши файлов исходного хранилища до и после проверки совпали.

## Подключение по TCP

Клиент и менеджер хранилищ используют общий `ТранспортХранилища`:
HTTP(S) делегируется прежнему коннектору, `tcp://` обращается напрямую к
TCP-серверу 1С без IIS и прокси. Формирование XML и разбор ответов общие.
Структура TCP-обмена сверена с [oproxy](https://github.com/infina15/oproxy):
приветствие `53F5C61A7B`, HTTP-подобный заголовок, XML и маркер `6653B2A6`.
oproxy служит источником сведений о протоколе, устанавливать его для CRS API не нужно.

```bsl
Клиент = Новый КлиентХранилища("tcp://localhost:1542/MyRepo", "8.5.1.1529");
Клиент.Подключиться("Администратор", "");
```

Имя можно передать третьим параметром `Подключиться` при адресе без имени.
Если имя указано обоими способами, оно должно совпасть. Порт по умолчанию — 1542.
Разбираются IPv4, DNS-имена и IPv6 в квадратных скобках; реальное IPv6-подключение
пока не проверено. Имена из пути TCP-адреса используются буквально, без URL-декодирования.

Каждый запрос открывает отдельное соединение и проверяет приветствие, код ответа,
Content-Length и маркер конца. Буфер сохраняет данные между чтениями и учитывает
разбиение или объединение сетевых блоков. На OneScript 1.8.2 ограниченное чтение
сокета зависает при избытке доступных байтов; транспорт читает доступные блоки
целиком и разбирает их самостоятельно. Таймауты чтения и отправки — 60 секунд;
подключение ограничивается системным сетевым таймаутом. Максимум тела запроса
или ответа — 256 МиБ, заголовка — 64 КиБ. Сжатие и chunked-кодирование ответов
не поддержаны. После ошибки транспорт не повторяет отправку, включая помещение.

На изолированном сервере 8.5.1.1529 проверены TCP-авторизация, получение описания
и объекта, захват и отмена захвата, инициализация основы и помещение изменения
корня с автоматическим продвижением основы. Версии совпали с HTTP; Конфигуратор
принял CF после TCP-помещения.

Дополнительно через TCP одним пакетом созданы справочник с реквизитом и табличной
частью, управляемая форма, модуль объекта и модуль формы. Модуль объекта размером
880 КБ содержит неповторяющиеся тестовые строки; бинарный пакет создания —
254 011 байт, изменения — 251 034 байта. Затем изменены комментарии справочника
и реквизита, привязка поля формы и оба модуля; справочник с формой удалён общим
механизмом. Все три помещения автоматически продвинули основу. На каждом шаге
независимый HTTP-кэш совпал с TCP по всем телам и потокам. Конфигуратор принял
CF; 30 файлов создания/изменения и 25 файлов после удаления совпали с его выгрузкой.
После удаления все нативные записи совпали с исходными, кроме списка версий.

По TCP проверены история и описания объектов старой версии, создание пользователя,
смена роли, деактивация и восстановление. Результаты сверены с HTTP; временная
учётная запись в конце деактивирована. Несуществующий пользователь не проходит
авторизацию. Создание самого хранилища по TCP отдельно не проверялось.

При проверке истории исправлены общие ошибки, затрагивавшие оба транспорта:
границы `beginVerNum`/`endVerNum` передаются атрибутами `value="-1"`, номер версии
читается как число, внутренняя версия — из значений атрибутов. Ошибка сервера
при чтении истории вызывает исключение, вместо возврата пустого списка.

Прямой RPC `DevDepot_devObjectsVersionEx` с историческим `verNum` вернул архив
версии создания уже удалённого справочника: все 16 объектов и 24 тела/потока
совпали с сохранённым CF этой версии. Это проверка протокола; отдельного публичного
метода выгрузки исторической версии в CF пока нет. `ПолучитьОбъект` по-прежнему
работает с актуальным описанием и не получает исторический снимок.

## Подготовка от различий CF

В ibcmd-rs передаётся полная целевая XML-выгрузка с сопутствующими файлами,
с исходным CF в качестве базы. Обратная выгрузка проверяется по всем входным
файлам, включая неизменённые; лишний или недостающий файл тоже отклоняется.
Текстовые и двоичные файлы обрабатываются без
списка разрешённых имён модулей. ConfigDumpInfo не является содержимым приложения.

Сначала используется `cf load --base`. При корректном отчёте компилятора об отказе
адаптер пробует `cf bootstrap --base-free` того же ibcmd-rs на полной целевой
выгрузке. Собственные преобразователи свойств не возвращаются. Отсутствие изменений,
таймаут и некорректный ответ процесса не запускают другой путь. Если полная сборка
тоже отклонена, сохраняются причины обоих отказов; пакет не формируется.

Полная сборка заново создаёт нативные тела и потоки. При сборке итогового CF
сохраняются исходные записи тех объектов, у которых не изменились путь,
полный набор принадлежащих им файлов и содержимое каждого файла. Это касается
тела и всех потоков объекта; дополнительные записи компилятора такого владельца
удаляются, пропущенные исходные восстанавливаются. Владельцы записей доказываются
общим классификатором CF; неизвестная запись остаётся ошибкой. Для изменённого,
нового или удаляемого объекта исходные записи так не подставляются.
После сборки проверяется обратная выгрузка всего итогового CF, включая сохранённые
объекты: расхождение с полным целевым деревом по-прежнему запрещает помещение.

План изменений, сохранение исходных записей и обратная сверка используют
один сравнитель содержимого файлов. BOM и CRLF/LF в UTF-8-тексте, XML-отступы
между элементами и порядок XML-атрибутов не создают изменений. Значения QName
сравниваются по пространству имён и локальному имени; смена привязки префикса
типа является изменением. Значения листовых элементов, значимый смешанный текст,
порядок дочерних элементов, `xml:space="preserve"`, пробелы кода и двоичные
данные сохраняют значение. Переименования, добавление и удаление файлов также
остаются изменениями. Одно форматирование не создаёт операций или захватов.
Отпечатки входных деревьев по-прежнему вычисляются по исходным байтам и
проверяются до и после компиляции: это отдельная защита от изменения входов.
UUID корня должен совпасть с основой; служебная запись `version` сохраняется
из связанного исходного CF. Совместимость этой привязки проверена Конфигуратором
8.5.1.1529: повторное сохранение не изменило тела и потоки. Затем обязательны
обратная выгрузка полного дерева, проверка каждого файла и прежние проверки
UUID, принадлежности, ссылок и графа. Диагностический режим отключения проверки
ibcmd-rs по-прежнему запрещён при подготовке помещения.

Через TCP проверены изменение существующей вложенной подсистемы, создание
подсистемы третьего уровня и её удаление. Конфигуратор принял CF на всех этапах:
27 файлов после изменения/удаления и 28 после создания совпали с основой.
Также помещены CodeLength 9 → 12 и UseStandardCommands true → false справочника;
результат подтверждён Конфигуратором. Исходные свойства после теста восстановлены.

`compiled_image.Delta` сравнивает все нативные записи двух CF: тела и потоки,
их добавление, изменение и удаление. Владельцы потоков определяются по UUID
и исходным метаданным хранилища. Неизвестная принадлежность записи останавливает
подготовку. Служебный список версий не помещается как объект; изменение указателя
корня или версии формата отвергается. Неизменённые тела не включаются в пакет,
кроме изменений служебной позиции. Изменение XML без нативных или позиционных
изменений не создаёт пакет.

На пути `cf load --base` изменённый компилятором связанный объект включается
и при неизменном XML. На пути полной сборки действуют описанные выше правила
сохранения целиком неизменённых владельцев файлов.
Для проверки его исходной версии сейчас заранее запрашиваются снимки всех
исходных объектов. Это увеличивает объём подготовки; выборочное получение
снимков после компиляции ещё предстоит. Сам кэш CF обновляется выборочно.

У CRS больше нет разрешённого списка XML-свойств или образцов новых реквизитов.
Нативные читатели проверяют итоговый состав UUID возможностей, генерируемые
идентификаторы и зависимости. Их покрытие классов и связей остаётся ограничением
служебного графа, отдельно от возможностей ibcmd-rs. Полная поддержка всех классов
метаданных пока не достигнута.

## Общие факты идентичности

`compiled_graph.read` получает из XML и CF UUID, имя, класс, родителя,
UUID возможностей и генерируемых типов, а также отдельно хранимых детей.
Класс дочернего объекта определяется коллекцией родителя в карте схемы;
для форм не требуется отдельное исключение по имени класса.

Декларации UUID должны присутствовать в нативном CF. Для объектов и встроенных
возможностей проверяется настоящая запись общих свойств с этим UUID;
генерируемые идентификаторы и возможности не могут пересекаться. Служебный UUID
класса, просто встречающийся в дереве, не становится возможностью объекта.
Для корня проверяются пары «класс — UUID» его внутренних объектов.
Состав хранимых детей сверяется с полным деревом выгрузки.

Общий читатель подключён к построению метаданных создания. Внешние потоки
берутся по принадлежности UUID из CF без списка имён модулей. На сохранённом
сценарии для всех 14 объектов хранилища подтверждено совпадение класса,
родителя, имени и UUID возможностей с серверными метаданными. Обобщение
зависимостей и расширение покрытия классов служебного графа — следующий этап.

## Общий индекс типов и зависимостей

В канонической подготовке `compiled_graph.TypeIndex` строится для исходного
и итогового CF. Все объявления `xr:GeneratedType` полной выгрузки дают имена
и UUID типов; принадлежность и идентичность подтверждаются общим читателем CF.
Для разрешения имени не требуется отдельная запись префикса или смещение
генерируемого типа в профиле класса. Поддерживаются полные имена вложенных типов.
Групповые типы связаны с проверенной возможностью корня, а не с UUID самого корня.

Из итогового индекса определяются владельцы используемых типов и зависимости.
Исходный индекс нужен для удаления ставших ненужными связей, включая ссылки
на объекты, отсутствующие в целевой выгрузке. Структурный родитель сохраняется.
Неопознанные исходные связи сохраняются, а не удаляются по предположению.

Проверка удаления также использует исходный TypeIndex: UUID объекта,
его возможностей и всех генерируемых типов подтверждаются по CF. Для удаления
вложенной возможности её типы выбираются по владельцу xr:GeneratedType.
Отдельные списки смещений типов для каждого класса и табличной части больше
не участвуют в этой проверке. Путь, пропускавший неизвестный класс при отсутствии
профиля снимка, удалён; проверка внешних ссылок требует привязанного исходного CF.

На сохранённых нативных данных проверено: оставленная в форме ссылка на Ref-тип
удаляемого ПВР отклоняется, очищенная ссылка разрешает пройти эту проверку.
Тот же механизм извлекает типы табличных частей. Подмена объявленного UUID,
отсутствие удаляемого объекта в исходном индексе и отсутствие самого индекса
завершают подготовку ошибкой. Это проверки адаптера без помещения на сервер.
Чтение ссылок внутри самих потоков форм, ролей и СКД по-прежнему ограничено
поддержанными форматами; произвольные двоичные данные не сканируются.

На текущей полной выгрузке подтверждены все 39 объявленных генерируемых типов.
Через HTTP последовательно изменён локальный реквизит формы: строка →
ReportObject → DocumentTabularSectionRow с полным именем владельца и табличной
части → строка. Сервер добавил и затем удалил зависимость от отчёта; после
восстановления скалярного типа осталась только связь с родителем. Конфигуратор
принял оба новых ссылочных варианта, XML совпал с целевым.

Индекс типов используется общим сборщиком графа. Покрытие нативных форматов
и внешних зависимостей подтверждается сквозными проверками, а не допуском по имени класса.

## Несколько внешних потоков одного объекта

native_streams определяет назначение каждого принадлежащего объекту потока.
Для управляемой формы .0 — общий пакет интерфейса и модуля, .1 — справка.
Назначения и пути экспорта берутся из общей карты native_asset_routes.json
на основе реестра ibcmd-rs (MIT-уведомление — IBCMD-LICENSE.txt).
Неизвестные принадлежащие объекту дополнения сохраняются сборщиком как
непрозрачные данные; при полной XML-подготовке неизвестный непустой поток
останавливает проверку полноты. Чужое имя потока отвергается.

Проверка зависимостей больше не требует единственного потока .0. Она читает
интерфейс формы, права роли и СКД из соответствующего основного потока даже
при наличии других. Повреждённые данные поддержанного структурированного
формата по-прежнему отвергаются. UUID-текст в справке, модулях и непрозрачных
данных не интерпретируется как ссылка на метаданные. Для макетов проверяется
СКД (вид 6); остальные виды сохраняются без анализа внутренних ссылок.

Изменение формы переведено на общую сборку нескольких потоков: изменившиеся
получают новые версии, неизменённые сохраняют версии, удалённые исключаются.
Однопоточная external_change удалена. Интерфейс .0 остаётся обязательным.

Проверены нативная форма регистра со справкой из демо-CF 8.5.1.1529 и сценарии
изменения/удаления справки, сохранения интерфейса и непрозрачного дополнения.
Добавление справки к форме справочника собрано ibcmd-rs штатным cf load --base:
полная обратная XML-выгрузка совпала с целевой; появился .1, содержимое .0
осталось побайтно исходным. Проверки прав и СКД, а также отказ при оставленной
ссылке на удаляемый ПВР работают при наличии дополнительных потоков.
Это проверки компилятора и адаптера без помещения на сервер.

## Общие описания объектов и граф

Для создания и изменения снят список допуска из четырёх классов. Общий
конструктор использует класс коллекции родителя, подтверждённые UUID и имя,
возможности из полного XML/CF, позицию и все принадлежащие объекту потоки.
Новые родители создаются раньше вложенных объектов. Идентификаторы генерируемых
типов существующих объектов сохраняются; удаление встроенной возможности
может удалить и принадлежащие ей типы.

`compiled_dependencies` определяет связи по подтверждённым нативным UUID,
владельцам генерируемых типов и хранимым детям. Родитель и структурные дети
сохраняют структурные связи. При изменении снимаются только связи, назначение
которых подтверждено исходным CF; непрозрачные исходные связи сохраняются.
Для прав и поддержанных макетов используются читатели внешних данных.
Приложение по-прежнему полностью преобразует ibcmd-rs.

Один общий пакет создал константу, перечисление и общий модуль; следующий
изменил все три объекта, добавил значение перечисления и изменил Module.bsl.
Конфигуратор принял CF: совпали все 29 файлов выгрузки и модулей, посторонние
нативные записи сохранились. Затем тем же конструктором создан параметр сеанса
с типом EnumRef; серверная зависимость от перечисления подтверждена с флагом 0,
его XML совпал с независимой выгрузкой Конфигуратора.
Все четыре тестовых объекта затем удалены одним общим пакетом. Конфигуратор
принял результат: записи CF побайтно вернулись к исходному состоянию, кроме
служебного списка версий; XML после удаления совпал с выгрузкой Конфигуратора.
Основа обновилась после создания, изменения и удаления.

## Что работает

- Управление пользователями, список версий и объектов версии, описание по UUID.
- Получение объекта, захват и отмена захвата.
- Отправка нативного пакета и проверка результата помещения.
- Сравнение полных XML-выгрузок с проверкой исходных версий.
- Подготовка одного пакета из полного результата ibcmd-rs с общими
  описаниями объектов и служебным графом. Сквозная матрица указана выше.

Для четырёх владельцев проверены комментарий и синоним; для формы — описание,
соседний Module.bsl и изменение полного Form.xml. Подключено
добавление/удаление реквизитов верхнего уровня владельца.
Для этих четырёх владельцев подключены ObjectModule и ManagerModule:
добавление, изменение, очистка текста и удаление файла. Потоки берутся
из CF ibcmd-rs целиком; неизменённые потоки сохраняют версии и не пересылаются.
Сквозной HTTP-сценарий проверен на справочнике; профили остальных трёх
владельцев проверены автоматическими тестами отображения потоков.
Первый реквизит и первая табличная часть документа с вложенными реквизитами
созданы одним общим пакетом. Состав возможностей считан из CF и сопоставлен
со всеми UUID полного XML объекта. Конфигуратор принял CF; все 25 файлов
совпали с целевой выгрузкой, посторонние нативные записи сохранились.
Отдельных методов создания реквизита или табличной части для этого не добавлялось.

Для Form.xml нет списка разрешённых видов элементов или образцов полей:
ibcmd-rs компилирует весь файл и проверяет обратную XML-выгрузку. CRS проверяет
уникальность идентификаторов в соответствующих коллекциях, привязки главного
реквизита к итоговому владельцу, объявленные ссылочные UUID и зависимости.
Форма без главного реквизита допустима; локальные реквизиты, параметры и
элементы обрабатываются целиком компилятором. Создание и изменение используют
одинаковую проверку результата. Кратность ссылочных UUID в потоке больше
не обязана совпадать с исходной формой: добавление и удаление использующих
их элементов законно. Возможности и ограничения ibcmd-rs сохраняются;
это не утверждение о проверке всех комбинаций свойств формы.

Ссылочные типы читаются общим механизмом метаданных из всех объявлений полного
Form.xml, включая параметры и вложенные колонки. Исключается только собственный
тип главного реквизита: его проверяет привязка к владельцу; типы его колонок
остаются самостоятельными зависимостями. Объявленный ссылочный UUID должен
присутствовать в нативной форме. При удалении последней ссылки убирается только
подтверждённая зависимость, неизвестные связи сохраняются.
Читатель типов определяет конфигурационные ссылки по URI пространства имён,
с учётом локальных объявлений `xmlns`, независимо от написания префикса.
Необъявленный префикс отклоняется. Это относится и к проверке типа главного
реквизита. Для исходных зависимостей сохраняется полный XML с объявлениями
пространств имён: повторная сериализация одного элемента ElementTree теряет
объявления префиксов, используемых только в текстовых значениях типов.
Эти проверки контракта не расширяют возможности XML-компилятора ibcmd-rs;
его обязательная проверка обратной выгрузки сохраняется.
Значения `xsi:type="…:DesignTimeRef"` используют тот же общий разбор областей
пространств имён. Локальное переопределение префикса допустимо; одноимённый
тип из постороннего пространства не создаёт зависимость. Объявление префикса
обязательно. На сохранённых нативных снимках проверены одинаковые UUID,
план зависимостей и контракт полной формы для перечислений, пустых ссылок
и предопределённых значений. Отдельный глобальный читатель объявлений удалён.
Добавление параметра с DocumentRef проверено настоящим ibcmd-rs 0.4.1 через
`cf load --base` для 8.5.1.1529: полная обратная XML-выгрузка совпала, изменились
только поток формы и служебная таблица версий CF. Нативный результат сохранён
в регрессионном тесте. Добавление и последующее удаление такого параметра
также прошли общий цикл подготовки, захвата и TCP-помещения в изолированную
копию хранилища. Повторно прочитанные серверные снимки подтвердили появление
и удаление зависимости от документа. Конфигуратор 8.5.1.1529 загрузил оба
полученных CF и подтвердил состав и тип параметров своей XML-выгрузкой.
После удаления прикладные XML и модули совпали с исходными, посторонние
нативные записи не изменились. Побайтовое восстановление самого потока формы
не гарантируется: ibcmd-rs нормализует его служебные поля и вспомогательные ID.

Подключён общий путь удаления отдельно хранимых дочерних объектов:
исчезновение определяется по полной XML-выгрузке, удалённые файлы исключаются
из дерева компилятора, из CF должны исчезнуть тело и все внешние потоки.
Изменённый родитель проходит те же общие проверки идентичности и коллекций.
В графе обновляются дочерние коллекции и признаки наличия объектов; исходные
описания удаляемых объектов сохраняются для запроса. Ссылка сохраняемого
объекта на удаляемую идентичность останавливает подготовку.

Сквозная проверка выполнена для удаления формы справочника, затем его
последней формы: HTTP-помещение, удаление потоков, обновление кэша и основы.
Остальные виды дочерних объектов требуют собственной сквозной проверки.

Корень конфигурации подключён к общему входу подготовки. Проверены
помещение комментария и версии, затем удаление справочника верхнего уровня.
Синоним также допускается контрактом общей текстовой части; отдельный
сквозной сценарий для него ещё не выполнен. Допускаемые Vendor, NamePrefix
и UpdateCatalogAddress пока отклоняет обратная проверка ibcmd-rs 0.4.1.

Коллекции корня читаются по схеме как `UUID класса, количество, UUID объектов`,
без привязки к номеру вложенного слота. Их состав сверяется с контекстом
хранилища. UUID возможностей корня должны сохраняться; изменение посторонних
нативных ссылок останавливает подготовку. После удаления очищаются только
связи, чьи целевые UUID действительно исчезли из нативного тела.

Создание справочников, документов, обработок и отчётов подключено к общему
входу. Все свойства и встроенные коллекции нового объекта компилирует ibcmd-rs;
прежние ограничения частичного изменения существующего объекта к его созданию
не применяются. Новые UUID объектов, встроенных возможностей и генерируемых
типов проверяются на пересечения; описания, позиции и граф строятся из CF.
Регистрируются модули ObjectModule/ManagerModule и ссылки на итоговые типы.
Проверенная HTTP-матрица: три справочника (включая модуль нового объекта),
последующее редактирование, новый документ, затем отчёт и обработка одним
пакетом. Конфигуратор принял итоговый CF со всеми четырьмя классами.

Подключено создание управляемых форм справочников, документов, обработок
и отчётов. Определение формы и весь поток интерфейса с модулем берутся
из CF ibcmd-rs. Класс, владелец, позиция, зависимости и внешние данные
включаются в общий пакет создания. Коллекция форм владельца сверяется
с нативным CF; необъявленные добавления и удаления отклоняются.
Создание формы существующему справочнику, изменение её модуля и создание
нового справочника вместе с формой проверены через HTTP и Конфигуратор.
Дополнительно через HTTP созданы формы документа, отчёта и обработки без
главного реквизита: локальная строка, вложенная группа, поле и надпись.
Затем изменены длина строки и заголовок надписи. На форме справочника добавлена
вложенная группа. Конфигуратор принял итоговый CF: все 15 файлов форм и модулей
совпали с целевыми, посторонние записи CF сохранились. Смена локальной строки
на CatalogRef и обратно подтвердила добавление и удаление зависимости формы
на сервере; XML ссылочного варианта совпал с выгрузкой Конфигуратора.
Основа продвинулась после каждого помещения.

При вставке перед существующим объектом пакет явно включает объекты со
сдвинутыми позициями. Позиции считаются по XML-коллекции отдельно для каждого
класса, не по сортировке файлов. Позиционное изменение получает новую версию
описания и тела при неизменных байтах приложения. Проверяется серверная
позиция каждого помещённого объекта. Самостоятельный ремонт несогласованной
позиции также возможен через общий вход, даже без изменения XML; повторная
компиляция неизменённого CF для него не запускается.

## Значения ссылок времени разработки

metadata_references больше не ограничен Enum.…EnumValue.… . Общий разбор
DesignTimeRef принимает именованные значения перечислений, EmptyRef объектов
с реально объявленным Ref-типом, пустое значение и предопределённые элементы
Catalog, ChartOfCharacteristicTypes, ChartOfAccounts, ChartOfCalculationTypes.
Тип подтверждается по CF, значение — по нативному потоку владельца:
соответственно .1c, .7, .9, .2. Собственные правила преобразования XML не нужны.

native_predefined_reader читает схемы колонок, сопоставление позиций, UUID,
имена и вложенные списки. Отвергаются дубликаты имён/UUID, несогласованные
счётчики и неправильная семья потока. Синтетический корень не является
предопределённым значением. Источник — проверенный итоговый CF либо полный
пакет текущей версии с проверкой версий тела и внешних потоков.

На тестовой конфигурации ibcmd-rs собрал поток справочника с двумя значениями
и управляемую форму с обоими значениями и EmptyRef в списке выбора. Вся обратная
XML-выгрузка совпала с целевой; адаптер подтвердил UUID типа, UUID значений и
нативную форму. Добавление и снятие зависимости формы, вложенные элементы,
план получения источников и отказ при устаревшей версии потока проверены тестами.
Помещение этого сценария на сервер не выполнялось.

Для трёх видов планов теперь проверены реальные эталоны 8.5.1.1529:

| Владелец значения | Компиляция формы, UUID и зависимости | Приём CF платформой |
| --- | --- | --- |
| План видов характеристик | Работает | Проверен |
| План счетов с включённым субконто (MaxExtDimensionCount=1) | Работает | Проверен |
| План видов расчёта | Работает | Проверен |

Во всех трёх случаях форма содержит именованное значение First и EmptyRef.
ibcmd-rs прошёл bootstrap и сверку всех файлов своей обратной выгрузки.
Конфигуратор принял каждый CF; в нативной выгрузке совпала изменённая форма,
остальные 32 файла совпали с нативной основой. Сервер хранилища в проверке
не участвовал. Нативные и скомпилированные потоки сохранены как статические
тестовые эталоны; собственные правила записи свойств не добавлялись.

Реальные эталоны исправили нумерацию колонок ПВХ (UUID в колонке 1, имя в 3)
и добавочное поле корня потока ПВР. XML-имя ChartOfCharacteristicTypes и
служебное имя ChartOfCharacteristicType разрешаются через общую карту схемы.
План получения типов при наличии CF использует его общий индекс деклараций.

Остаются два конкретных ограничения. При MaxExtDimensionCount=0 ibcmd-rs 0.4.1
пропускает Predefined.xml плана счетов при выгрузке, хотя нативный поток читается
нашим адаптером. Проверка полноты сопоставляет непустые нативные потоки с файлами
XML: неполная основа или экспорт прекращают подготовку до сборки пакета. Та же
проверка действует при инициализации/продвижении основы и получении новой версии
в Git. Существование пустого потока само по себе не требует файла с данными.
Такой сценарий помещения с нулевым количеством субконто остаётся заблокирован
ограничением компилятора; отказ не обходится.
Для значений ПВР основной путь с проверенным CF работает, а отдельное разрешение
только по пакету версии без индекса CF пока требует отсутствующего профиля типов
и явно отклоняется. ПВХ и план счетов проверены также по пакету текущей версии.
Ссылки в произвольных непрозрачных потоках и пары UUID без имени не добавлены.

## Полнота CF → XML

`export_coverage.require_complete_export` сопоставляет нативные потоки с файлами
по 95 маршрутам общей карты. Проверка действует до компиляции, на обратном
экспорте результата, при инициализации/продвижении основы и обновлении Git.
Она учитывает внутренний UUID корня и UUID вложенных команд, а не только
объекты с отдельным XML-файлом.

Для формы обязательны Form.xml и, если нативный модуль непустой, Form/Module.bsl.
Свойства и элементы интерфейса эта проверка не разбирает. Для обычных модулей
различаются текстовые BSL и двоичные BIN, включая вложенные контейнеры
Format15/Format16. Справка требует индекса с теми же языками, всех HTML-страниц
и вложений; индекс картинки — указанного двоичного файла. Вид макета определяет
расширение его полного файла. Пустота допускается только при известном формате:
пустой текст модуля, пустая справка/Predefined и подтверждённая пустая запись
командного интерфейса; неизвестный непустой поток не считается пустым.

Это контроль наличия представления и составных файлов, а не доказательство
равенства каждого XML-свойства нативному содержимому. Полное сравнение целевой
и обратной выгрузок остаётся обязательным. Скрытое изменение данных внутри
поддержанного компилятором формата требует отдельного нативного эталона.

На сохранённой демо-конфигурации проверены все 340 внешних потоков; пропущенных
файлов по этой карте не обнаружено. Также проверены три CF лаборатории,
включая форму с модулем и справкой и планы с предопределёнными значениями.
Отрицательные тесты удаляют модуль, страницу, вложение или картинку; неполный
экспорт не публикует новую основу и не меняет рабочую папку.

## Сквозная проверка большой конфигурации

На полном демо-CF (380 объектов, 723 записи) получение из хранилища и сборка
кэша выполнены. XML-основа не опубликована: ibcmd-rs 0.4.1 отклонил 10 потоков
форм с вложенными условиями оформления. Отдельно непрозрачными остались
прикладные записи корня (interface_compatibility_pair), критерия отбора
(filter_criterion_owner) и предопределённых данных справочника. Служебные
root/version/versions в отчёте opaque не являются пропущенными объектами XML.
Помещение полного демо остаётся заблокировано; неполная выгрузка не используется.

Отдельное изолированное хранилище с 217 поддержанными объектами прошло смешанное
помещение: CodeLength справочника, общий модуль, интерфейс и модуль формы,
новый модуль сеанса, создание константы и удаление другой. В пакете одно
создание, одно удаление и семь существующих объектов. Все 230 файлов совпали
с независимой выгрузкой Конфигуратора; прочие записи CF сохранились. При первом
помещении основа восстановлена по квитанции после исправления получения потоков,
без повторной отправки пакета.

Второй смешанный пакет (одно создание, одно удаление, пять существующих объектов)
прошёл автоматически, включая получение серверных изменений и продвижение
основы. Его 230 файлов также совпали с независимой выгрузкой Конфигуратора.
Тестовые захваты сняты; повторное обновление без изменений не запускалось.

Проверка выявила и исправила три общих ограничения адаптера:

- Внешний поток может называться по UUID внутреннего объекта корня или вложенной
  команды. Принадлежность определяется объявленными возможностями метаданных;
  чужие и пересекающиеся UUID отвергаются. Сборка, сравнение CF и выборочное
  получение кэша больше не требуют префикса UUID самого объекта.
- Полный пакет версии ограничен 256 МиБ отдельно от лимита одной нативной записи
  в 16 МиБ. Проверки индекса и контрольных сумм сохранены; большая версия
  не разрешает увеличенный размер отдельной записи.
- Последний блок многостраничного индекса CF завершается маркером конца;
  лишний пустой блок больше не создаётся. Исправленный CF принят ibcmd-rs
  и Конфигуратором.

## Что пока не подключено

Поддержка объекта компилятором ещё не означает поддержку его графа помещения.
Текущий адаптер явно отклоняет:

- Форматы определения объекта без подтверждаемой записи общих свойств
  и коллекции класса в карте схемы; объекты с ненулевым служебным owner_id.
- Изменения UUID корня вне дочерних коллекций, если их нельзя подтвердить как
  ссылки на реальные объекты, их возможности или генерируемые типы. Собственные
  UUID корня и непрозрачные нативные константы остаются защищёнными.
- Смену класса или родителя существующего UUID. Перенос к другому владельцу
  оформляется удалением старого объекта и созданием нового UUID.
- Дочерние структуры вне покрытых нативными читателями коллекций.
- Ссылочные типы, не объявленные в полной выгрузке и не входящие в проверенные
  группы платформы; значения ссылок времени разработки вне подтверждённых
  именованных форматов и нативных потоков Predefined. Произвольные пары UUID
  без доказанного владельца не принимаются. Для главного реквизита используются
  типы его поддержанного владельца.
- Новые нативные записи, принадлежность которых нельзя установить из UUID
  и исходных внешних данных; связанный объект без контракта служебных метаданных.

Обычные формы исключены. Возможности удалённого собственного сериализатора
больше не являются доступными методами подготовки. Входы по одному XML и
старые имена классов пакетов удалены.

## Проверка границ адаптера и компилятора

В основном пути подготовки нет списка разрешённых классов или XML-свойств:
полные файлы обрабатывает ibcmd-rs. Оставшиеся ограничения следует различать:

| Область | Что ограничивает работу |
| --- | --- |
| Свойства XML, типы, элементы управляемых форм | Возможности ibcmd-rs и совпадение полной обратной выгрузки; Python не добавляет правила записи свойств |
| Общие UUID объекта, генерируемые типы и хранимые дети | Нативные читатели CRS и карта схемы; новый формат требует подтверждения структуры |
| Ссылки корня конфигурации | Подтверждение UUID по исходному и итоговому CF; общий запрет любых изменений ссылок снят |
| Значения ссылок времени разработки, непрозрачные потоки и неизвестный владелец записи | Покрытие читателей CRS и контракт метаданных хранилища |
| Смена класса или родителя при сохранении UUID | Сознательное ограничение модели: удаление и создание с новым UUID |
| Ненулевой служебный owner_id и форматы вне выбранного профиля | Неподтверждённый контракт хранилища; поддержка компилятором сама по себе недостаточна |
| Лимиты размера и числа объектов | Ограничения CRS, отдельные от возможностей ibcmd-rs |
| Обычные формы | Исключены из объёма проекта |

Первый снятый лишний запрет — изменение ссылок корня вне дочерних коллекций.
На сохранённом CF проверено очищение DefaultLanguage: ibcmd-rs прошёл полную
сборку bootstrap и сверку всей обратной выгрузки; восстановление языка также
прошло компиляцию и полную сверку. Прежний счётчик UUID CRS отклонял результат. Теперь исходная и итоговая ссылки доказываются по общему
индексу идентичности; зависимости пересчитывает compiled_dependencies.
Подготовка принимает очищение ссылки и её восстановление из сохранённого CF.
Это проверка компиляции и адаптера без помещения на сервер.

Неизвестные изменённые UUID, дополнительные вхождения собственных UUID корня,
подмена нативной идентичности объекта ссылки и сохранившаяся ссылка на удалённую
идентичность отвергаются. Неизменённые непрозрачные константы сохраняются.
Проверка полного XML остаётся обязательной; это не обход отказов ibcmd-rs.

## Ограничения ibcmd-rs 0.4.1

Удаление формы проходит штатный `cf load --base` и обратную сверку.
Первый отказ теста был вызван лишней пустой строкой в XML владельца после
удаления тега, а не отсутствием нативной поддержки. Исправленная выгрузка
прошла проверку без диагностических режимов. Адаптер не допускает переменную
`IBCMD_RS_LOAD_NO_VERIFY`, отключающую проверку компилятора.

Для реквизитов объектов проверены 24 сценария. Результат одинаков для четырёх
владельцев; это отдельная матрица от локальных реквизитов формы:

| Изменение | Результат |
| --- | --- |
| Добавить строковый реквизит | Работает |
| Удалить реквизит вместе с полем формы | Работает |
| Добавить реквизит вместе с полем формы | Работает |
| Добавить новый реквизит DocumentRef вместе с полем формы справочника | TCP-помещение и независимая выгрузка Конфигуратора подтверждены; остальные владельцы отдельно не проверены |
| Заменить существующий тип Строка на Число(10,2) | Полная сборка, TCP-помещение и Конфигуратор подтверждены для справочника; остальные владельцы отдельно не проверены |
| Заменить существующий тип на ДокументСсылка и вернуть строку | Те же проверки прошли для справочника; UUID реквизита и нативная форма сохранились |
| Заменить существующий тип на СправочникСсылка | Полная сборка, TCP-помещение и Конфигуратор подтверждены для ссылки на собственный справочник; другой владелец ссылки отдельно не проверен |
| Удалить реквизит, оставив поле формы | Конфигуратор отклоняет неверный DataPath |

`SequenceFilling=AutoFillOff` документа прошёл полную сборку, TCP-помещение
и независимую XML-выгрузку Конфигуратора 8.5.1.1529. Изменение выполнено одним
пакетом вместе со сменой типа реквизита справочника на самоссылку CatalogRef;
обратным пакетом восстановлены оба объекта. UUID реквизита сохранился, в графе
сервера нет зависимости объекта от самого себя. Неизменённые формы и прочие
посторонние записи CF остались побайтово исходными, прикладные файлы восстановились.
Этот сценарий не требовал правил записи отдельных свойств или типов в CRS.
Остальные варианты постоянных типов этой матрицы пока не подтверждены.

Создание нового реквизита справочника с типом `DocumentRef` и поля управляемой
формы выполнено одним общим пакетом. Следующим пакетом удалены оба. Снимки
сервера подтвердили появление и удаление UUID реквизита в составе возможностей
и зависимости владельца от документа. Конфигуратор 8.5.1.1529 загрузил оба CF
и подтвердил тип и DataPath своей XML-выгрузкой. После удаления прикладные XML
и модули восстановились, посторонние нативные записи сохранились. Все три
состояния сохранены в регрессионном тесте; новая форма отклоняется при проверке
по старому владельцу или после удаления реквизита. Создание и смена типа
существующего реквизита проверяются отдельными сценариями.

Смена типа существующего реквизита справочника дополнительно прошла полный
цикл помещения: Строка → Число(10,2) → Строка → ДокументСсылка → Строка.
Полная сборка сохраняет неизменённые объекты перед обратной проверкой; раньше
её блокировали добавленные компилятором свойства посторонней формы документа.
Конфигуратор подтвердил три типа, UUID реквизита и DataPath существующего поля
формы. Серверная зависимость от документа появилась и исчезла после возврата
к строке. Все посторонние нативные записи, включая формы, остались побайтово
исходными; прикладные XML и модули восстановились. Нативные состояния сохранены
в регрессионном тесте без собственных правил записи типов.

ibcmd-rs и Конфигуратор могут по-разному назначать XML ID служебным элементам
форм с нулевыми нативными ID. Неизменённые файлы берутся из собственной выгрузки
ibcmd-rs; неизменённые нативные записи обязаны остаться исходными.
Произвольные расхождения идентификаторов не игнорируются.

## Подготовка пакета

Нужны OneScript, Python 3.9+ (только стандартная библиотека),
исполняемый файл ibcmd-rs и актуальный CF. base_cf должен соответствовать исходной
конфигурации: тела и потоки затронутых объектов сверяются со снимками хранилища.

```bsl
Компилятор = Новый Структура("backend,executable,base_cf",
    "ibcmd", "C:\tools\ibcmd-rs.exe", "C:\work\current.cf");
Пакет = Клиент.ПодготовитьКонфигурациюИзВыгрузки(
    "C:\work\target", "C:\work\baseline",
    "C:\Python39\python.exe", Компилятор);
```

Обе папки — полные иерархические выгрузки. Исходная содержит актуальный
ConfigDumpInfo.xml. Текст модуля формы берётся из <форма>/Ext/Form/Module.bsl,
интерфейс — из <форма>/Ext/Form.xml. Подготовка не захватывает объекты и не
отправляет изменения. После проверки пакета вызывающая сторона захватывает
его объекты и вызывает Клиент.ПоместитьПакет(Пакет, Комментарий).

Цепочка: нормализация активного контейнера CF → cf export --index → полные
изменённые файлы → cf load --base → контрольная выгрузка → проверка UUID и графа
→ единственная упаковка пакета хранилища. XML переносится целиком; согласуется
только заголовок пространств имён с проверкой QName и смысла документа.

Потеря свойства, изменение посторонней нативной записи, неподдержанная операция
или устаревший снимок прекращают подготовку. Лимиты: 240 секунд на команду,
CF 256 МиБ, распакованный образ 512 МиБ; отдельные записи ограничены читателем.

## Инициализация основы правок

`ИнициализироватьОснову` автоматически получает текущую версию хранилища,
собирает начальный CF и экспортирует неизменяемую XML-основу через ibcmd-rs.
Исходный CF и Git не обязательны. Пример после подключения клиента:

```bsl
Настройки = Новый Структура("backend,executable,cache_directory",
    "ibcmd", "C:\tools\ibcmd-rs.exe", "C:\work\.crs-cache");
Основа = Клиент.ИнициализироватьОснову(
    Настройки, "C:\work\xml", "C:\Python39\python.exe");
// Меняем файлы в Основа.working_directory.
Пакет = Клиент.ПодготовитьКонфигурациюИзВыгрузки(
    Основа.working_directory, Неопределено, "C:\Python39\python.exe",
    Основа.compiler_settings);
```

Если рабочая папка не передана, создаётся `<cache_directory>/workspaces/<id>/xml`.
Существующая полная XML-выгрузка принимается при совпадении корня и всех версий
`ConfigDumpInfo.xml` с текущим хранилищем; её файлы сохраняются без изменений.
Локальные правки при этом остаются правками относительно полученной основы.
По старой или неизвестной выгрузке восстановить историческую основу нельзя.
Рекомендуется править созданную `working_directory`: внешний XML Конфигуратора
может отличаться от ibcmd-rs вспомогательными ID формы, и такие отличия
будут видны как изменения, даже при одинаковой версии в ConfigDumpInfo.

Основа хранится отдельно в `baselines/<id>/xml`; `baseline.json` указывает
на её манифест с UUID хранилища, версией, поколением CF и контрольными суммами.
Само обновление CF не меняет основу правок. После подтверждённого помещения
она продвигается автоматически, как описано ниже. Повторный явный вызов создаёт новую
основу, сохраняя предыдущую; существующая рабочая папка проверяется заново.
Ошибка до публикации оставляет предыдущую основу активной. Рабочая папка
не может находиться внутри неизменяемых снимков или содержать сам кэш.

Без Git подготовка с неявной основой прекращается, если сервер уже перешёл
на другую версию: нужно согласовать входящие изменения и передать новую
исходную папку либо явно инициализировать новую основу. Для автоматического
трёхстороннего согласования включается `use_git = Истина` в настройках.
Инициализация сама по себе не захватывает объекты и не выполняет помещение.

Первичная автоматическая сборка использует служебный профиль legacy,
проверенный на 8.5.1.1529. Более ранние версии принимаются по общей политике
совместимости, но отдельно не проверены. Для других профилей требуется
проверенный `seed_cf`. Полный пакет версии ограничен 256 МиБ, отдельная нативная запись — 16 МиБ.

## Подготовка с получением и захватом

`Клиент.ПодготовитьПомещениеКонфигурации` возвращает
`ПодготовкаПомещенияКонфигурации`: подготовленный пакет, фактические пути
`ПапкаXML`/`ИсходнаяПапкаXML`, `ВерсияХранилища`, списки `НовыеЗахваты` и
`ПрежниеЗахваты`, а также `Состояние`. Нужен `cache_directory` и известная
XML-основа. Прежний `ПодготовитьКонфигурациюИзВыгрузки` остаётся отдельной
операцией подготовки пакета без автоматического захвата.

Сначала обновляется CF-кэш. При `use_git = Истина` входящие изменения
согласуются прежним механизмом Git; без Git устаревшая неявная основа
останавливает подготовку до захватов. Конфликт также прекращает подготовку.
Оригинальная XML-папка сохраняется; фактическая рабочая копия видна в `ПапкаXML`.

План `capture_ids` содержит UUID изменяемых и удаляемых существующих объектов,
включая родителей новых объектов. Новые UUID захватывать до создания не нужно.
Этот набор захватывается до компиляции, затем повторно проверяется версия
хранилища. Если компилятор изменил дополнительные объекты, они захватываются
и проверяются после компиляции до возврата готового результата. Снимки всех
исходных объектов пока по-прежнему заранее доступны из кэша; захват всех
неизменённых объектов не выполняется.

```bsl
Подготовка = Клиент.ПодготовитьПомещениеКонфигурации(
    ПапкаXML, Неопределено, ПутьPython, Компилятор);
Если Подготовка.Пакет <> Неопределено Тогда
    Результат = Подготовка.Поместить("Согласованные изменения");
КонецЕсли;
// До помещения можно отказаться: Отмена = Подготовка.Отменить();
```

Прежние собственные захваты не перезахватываются и не освобождаются.
Новый захват проверяется по владельцу, номеру версии и исходной строке
`reviseDate`. При отмене или ошибке подготовки предпринимается снятие только
захватов этой операции. Заменённый захват или чужой владелец не освобождается;
ошибка перечисляет UUID, которые не удалось освободить. Результат `Отменить()`
содержит `Освобождены`, `НеОсвобождены`, `Ошибки`. Служебный порядок захватов
хранится отдельно от экспортируемых отчётных массивов.

`Поместить()` ещё раз проверяет пакет, захваты и версию, выполняет одно помещение
и после подтверждения и обновления основы снимает собственные захваты.
Учитываются и автоматические захваты созданных сервером объектов: перед снятием
проверяется локальная версия созданного объекта. Прежние захваты сохраняются.
После начатой попытки помещения повторная отправка через этот результат
подготовки запрещена.

| Состояние | Значение и допустимое продолжение |
| --- | --- |
| `Готово` | Пакет и захваты проверены; можно поместить либо отменить подготовку |
| `НетИзменений` | Пакет отсутствует, захватов нет |
| `Восстановлено` | Прежний процесс завершён до отправки; можно отменить захваты и подготовить новый пакет |
| `Отменено` | Захваты подготовки освобождены |
| `ЗахватыНеОсвобождены` | Есть ошибки снятия; можно повторить отмену |
| `Помещено` | Помещение и основа подтверждены; повторная отмена только повторяет незавершённое снятие захватов |
| `ИсходНеизвестен` | Исключение при вызове помещения; захваты сохраняются, отправка и отмена запрещены до подтверждения |
| `ПомещеноОсноваНеОбновлена` | Сервер подтвердил помещение; можно повторить обновление основы либо явно освободить захваты |

`Подготовка.ПодтвердитьПомещение()` повторяет только получение и продвижение
основы по существующей квитанции, проверяя ожидаемое содержимое сервера.
Пакет не отправляется повторно. Если подтверждение не получено, состояние
и захваты сохраняются. Отмена после уже подтверждённого помещения освобождает
захваты, а не откатывает изменения сервера.

Подготовка ведёт журнал в `<cache_directory>/preparations/<UUID>`: состояние,
состав и метки захватов, неизменяемый пакет и контекст квитанции. Пароли туда
не записываются. Каталог доступен как `Подготовка.КаталогПодготовки`; при ошибке
подготовки он включается в сообщение. Журнал записывается до сетевых изменений.
Вход требует уже инициализированную основу в кэше.

После завершения прежнего процесса подготовку можно явно восстановить:

```bsl
Подготовка = Клиент.ВосстановитьПодготовкуПомещения(КаталогПодготовки, ПутьPython);
// Для прерванной отправки — только проверка результата и продвижение основы:
Итог = Подготовка.ПодтвердитьПомещение();
// Для подготовки, которая ещё не отправлялась, — отмена её захватов:
// Итог = Подготовка.Отменить();
```

Восстановление проверяет хранилище, платформу, пользователя, контрольные суммы
журнала и пакета. Живой процесс сохраняет владение; его подготовку перехватить
нельзя. Прерванная отправка становится `ИсходНеизвестен`, неотправленная
подготовка — `Восстановлено`. Восстановленный объект не предоставляет готовый
`Пакет` и никогда не отправляет сохранённый пакет повторно. Неподтверждённое
помещение сохраняет захваты до выяснения результата. После отмены до отправки
нужно выполнить новую подготовку.

Владелец в протоколе — пользователь хранилища; отдельного уникального токена
операции statMap не даёт. Если процесс завершился между захватом и получением
его метки, такой захват автоматически не снимается: требуется проверка владельца.
Журналы и сохранённые пакеты автоматически не очищаются.

На изолированном хранилище 8.5.1.1529 проверены сохранение прежнего захвата,
снятие новых после помещения и отмены, откат захватов после отказа ibcmd-rs,
отказ при чужом захвате с сохранением его владельца и отсутствие захватов
без изменений. Создание константы подтвердило автоматический захват нового
объекта сервером и его освобождение вместе с захватом родителя. Согласование
изменений другого пользователя через Git выполнено до захвата локального
объекта; обе правки сохранились, исходная папка не изменилась. Независимые
выгрузки Конфигуратора совпали по всем 29/31/31 файлам трёх сценариев.
Дополнительно на сервере воспроизведены изменение объекта между получением
версии и захватом, смена владельца захвата во время компиляции и изменение
незахваченного родителя подготовленной формы. Устаревшие операции не помещены,
чужие захваты сохранены. Восстановление после завершения процесса проверено
для отмены неотправленной подготовки и для потери TCP-ответа: сервер принял
помещение, клиент был принудительно завершён до получения ответа, новый процесс
подтвердил результат и снял захваты. В последнем сценарии зарегистрирован ровно
один вызов помещения. Отказ обновления основы, заменённая метка и другие переходы
дополнительно проверены имитацией клиента.

## Обновление основы после помещения

Для пакета, подготовленного через `cache_directory` с инициализированной
основой, обновление выполняется автоматически после подтверждения всех
объектов сервером в `ПоместитьПакет`. Перед отправкой сохраняется квитанция
`pending/<id>/receipt.json`: хеш пакета, неизменяемый XML-снимок, UUID основы,
ожидаемые версии объектов и потоков и хеши всех итоговых нативных записей.

После помещения кэш получает серверные изменения. Для продвижения основы
должны совпасть состав записей, их содержимое, классы, родители и версии
объектов/потоков. Исходный UUID версии должен смениться. Дополнительные
неучтённые изменения другого разработчика останавливают продвижение.
Рабочие файлы сохраняются: в новую основу попадает отправленный снимок,
а `ConfigDumpInfo.xml` берётся из проверенного серверного CF. Так следующие
локальные правки не становятся частью уже отправленной основы, а ID форм
сохраняют представление отправленного XML.

```bsl
Результат = Клиент.ПоместитьПакет(Пакет, "Описание изменения");
Состояние = Пакет.СостояниеОсновы;
Если Не Состояние.updated И Состояние.committed Тогда
    // Сервер уже принял пакет. Повторяем только обновление основы.
    Состояние = Клиент.ОбновитьОсновуПослеПомещения(Пакет);
КонецЕсли;
// При updated = Истина: baseline_directory, working_directory, repository_version.
// При updated = Ложь: error; прежняя основа остаётся активной.
```

Ошибка получения, экспорта или публикации основы после успешного помещения
не выдаётся за ошибку отправки: `ПоместитьПакет` возвращает подтверждённый
серверный результат, а `Пакет.СостояниеОсновы` сообщает `committed = Истина`,
`updated = Ложь` и причину. Повторный вызов обновления не отправляет пакет;
повтор уже выполненного продвижения не создаёт другую основу. Пакеты без
сохранённого контекста основы работают без автоматического продвижения.

При подготовке с неявной основой используется её `working_directory`.
После Git-согласования это может быть новая рабочая копия; её путь возвращается
в `Пакет.СостояниеОсновы`. Исходная папка не переписывается. Подготовка другой
папки с неявной основой отклоняется; для неё нужно передать явную исходную
XML-папку. При `use_git = Истина` продвижение основы сразу фиксирует
полученную после помещения версию в служебной ветке `codex/crs-repository`.
В `СостояниеОсновы` возвращаются `repository_commit`, `source_branch`
и `git_directory`. Без Git настройки и поведение остаются прежними.
Если Git недоступен, отправка остаётся подтверждённой, а обновление основы
можно повторить. Сбой после Git-коммита до публикации основы не создаёт
дубликат при повторе: уже записанная версия используется повторно.
Старые основы и квитанции автоматически не очищаются. Для составной подготовки
квитанция восстанавливается через `ВосстановитьПодготовкуПомещения`; отдельный
старый пакет без журнала этим входом не восстанавливается.

## Инкрементальный кэш исходного CF

В общем входе подготовки можно указать `cache_directory` вместо `base_cf`:

```bsl
Компилятор = Новый Структура("backend,executable,cache_directory",
    "ibcmd", "C:\tools\ibcmd-rs.exe", "C:\work\.crs-cache");
Пакет = Клиент.ПодготовитьКонфигурациюИзВыгрузки(
    "C:\work\target", "C:\work\baseline", "C:\Python39\python.exe", Компилятор);
```

`seed_cf` — необязательный исходный CF для первого создания кэша. Если он
передан, должен соответствовать текущему состоянию хранилища; сверяются корень,
состав записей и версии объектов/потоков. Без него первая загрузка получает
полный нативный пакет текущей версии и собирает служебные записи CF.
Далее CF обновляется автоматически перед подготовкой: запрашивается свежий
контекст, сравниваются версии каждого объекта и его внешних потоков. Тела и
потоки скачиваются выборочно через `DevDepot_updateObjects`; полная версия
хранилища не скачивается. Вместе с изменённым потоком сервер возвращает тело
его объекта, которое также сверяется. Удалённые записи убираются из кэша.

Служебная запись `versions` CF обновляется отдельно от учёта версий хранилища.
Нативное содержимое объектов не преобразуется. CF перепаковывается локально;
неизменённые тела и потоки сохраняются побайтно. Снимки для помещения и пакет
версии для проверки зависимостей также собираются из кэша и свежего контекста,
без повторного скачивания полных данных с сервера.
Общий лимит локального пакета исходных данных, снимков и контекста — 256 МиБ,
отдельной нативной записи и её распакованного содержимого — 16 МиБ. Общий
декодер проверяет размер до и после base64-декодирования; увеличенный контейнер
не ослабляет ограничения записей и проверки контрольных сумм. На данных кэша
проверена подготовка исходного пакета больше 24 МиБ с двумя неповторяющимися
потоками по 12 МиБ: оба потока прочитаны побайтно без потерь. Это проверка
сборки и чтения исходных данных, а не серверного помещения такого размера.
Локальные ограничения итогового пакета в 32 МиБ и 256 объектов сняты.
Число объектов группы проверяется по её составу, UUID и исходным описаниям;
отдельного числового потолка нет. Бинарный конверт ограничен 256 МиБ, а полный
HTTP/TCP-запрос — теми же 256 МиБ после UTF-8-кодирования, с учётом XML и base64.
Поэтому практически допустимый бинарный пакет меньше 192 МиБ: точная граница
зависит от описаний объектов и прочих полей запроса. Общая проверка выполняется
до открытия TCP-соединения или вызова HTTP-коннектора. Ограничения отдельных
нативных записей и распаковки не изменены.

Локально проверены сборка и обратное чтение нативного конверта больше 32 МиБ
с 300 объектами (включая четыре неповторяющихся тела по 9 МиБ) и сохранением
контрольных сумм. OneScript сформировал XML-конверт больше 33 МиБ с 260
изменениями, одним созданием и одним удалением; дубликат UUID и превышение
предела сообщения отвергаются. Это проверки формата и клиентской валидации,
а не доказательство принятия большого пакета сервером.

Отдельно сервером 8.5.1.1529 через TCP принят пакет **40 116 480 байт**:
264 изменения, одно создание и одно удаление. В бинарном пакете 265
создаваемых/изменяемых объектов; удаление передаётся отдельно. Четыре общих
модуля содержат примерно по 12,5 МиБ неповторяющегося текста. Конфигуратор

Большая группа выявила ограничение скорости: проверки помещения и обновление
кэша повторяют чтение описаний для каждого объекта. На тестовом хранилище
чтение одного описания занимало около трёх–пяти секунд; полный прогон с

78 минут. Пакетное чтение описаний и статистики ещё предстоит.

Отдельный вызов обновления:

```bsl

    Неопределено, "C:\Python39\python.exe");
// Кэш.base_cf — путь к актуальному CF; fetched_ids/fetched_streams — статистика.
```

Каталог содержит `current.json` и неизменяемые поколения
`generations/<id>/base.cf` с `repository-state.json`. Учитываются UUID хранилища,
корня, версия платформы и версии всех объектов/потоков. Контрольные суммы
обнаруживают повреждение кэша. Параллельная запись блокируется, новый указатель
публикуется только после успешной сборки. Старые поколения автоматически не
удаляются; оставшийся после аварии `write.lock` требует проверки процесса.
Каталог `.crs-cache` исключён из Git.

Смена версии хранилища во время чтения останавливает обновление. Скомпилированный
целевой CF не становится источником автоматически: кэш обновляется только из
подтверждённого состояния сервера. Основа XML хранится отдельно; согласование
через Git включается явно, как описано ниже. Кэш не расширяет ограничения адаптера помещения.

операцией полной выгрузки версии и без запросов тел из прогретого кэша.
Изменение пакета проверено, в хранилище оно не отправлялось.

Добавления/удаления записей, отдельное изменение/удаление потока, устаревшие
снимки, повреждения и прерванная публикация поколения покрыты автоматическими
тестами. Реальный HTTP-сценарий пока проверен для изменений существующих объектов.

## XML-проект Git и согласование входящих изменений

При использовании `cache_directory` и `use_git = Истина` подготовка ведёт
отдельный Git-проект. По умолчанию это bare-репозиторий `<cache_directory>/xml.git`;
путь можно изменить настройкой `xml_repository`, а ветку полученных версий —
настройкой `source_branch`. Нужен Git с поддержкой
`merge-tree --write-tree --merge-base`; проверено на Git 2.55.0 для Windows.

Для общего входа подготовки включите Git явно:

```bsl
Компилятор.Вставить("use_git", Истина);
Компилятор.Вставить("source_branch", "storage/incoming"); // необязательно
```

- `source_branch` содержит XML-снимки полученных версий хранилища; по умолчанию
  это `codex/crs-repository`. Принимаются короткое имя (`storage/incoming`)
  и полное (`refs/heads/storage/incoming`); в отчёте возвращается короткое.
  Имя проверяется до записи Git. Зарезервированные рабочие ветки
  `codex/crs-work/<id>` и их родительские имена выбрать нельзя.
  Каждая новая полученная версия фиксируется отдельным коммитом с UUID версии,
  UUID хранилища, корнем и платформой. Повтор той же версии не создаёт дубликат.
- `codex/crs-work/<id>` содержит результат слияния локальных правок с полученной
  версией. Для него создаётся настоящая рабочая копия Git.
- Исходные папки пользователя не переписываются. Новая основа, рабочая копия
  и отчёт находятся в `<cache_directory>/xml-runs/<id>/`.

Три стороны слияния: переданная исходная XML-папка, локальная целевая папка и
XML из актуального CF кэша. Git объединяет независимые изменения, включая
добавления и удаления. При конфликте подготовка пакета прекращается, а
`report.json` перечисляет конфликтующие файлы. Полученная версия хранилища
при этом остаётся сохранённой в служебной ветке. Выбранная `source_branch`
проходит через настройки OneScript и сохраняется в квитанции помещения.
Продвижение основы и его повтор используют ветку из квитанции. Смена настройки
на другую ветку создаёт отдельную историю, не переименовывая прежнюю.

Для ручного разрешения создайте согласованную целевую папку на основе
`baseline_directory` из отчёта, сохранив нужные локальные правки, и передайте
её вместе с этой новой основой в повторный вызов подготовки. Исходная рабочая
папка остаётся доступной по `original_directory`. Автоматического выбора
победителя при конфликте нет.

```bsl
// Копируем Отчёт.baseline_directory в отдельную папку «resolved»,
// затем переносим в неё нужные локальные правки и разрешаем конфликт.
Пакет = Клиент.ПодготовитьКонфигурациюИзВыгрузки(
    "C:\work\resolved", Отчёт.baseline_directory,
    "C:\Python39\python.exe", Компилятор);
// Перед помещением захватываем Пакет.СуществующиеОбъекты.
Клиент.ПоместитьПакет(Пакет, "Согласованные изменения");
// Следующие правки делаем в Пакет.СостояниеОсновы.working_directory.
```


Это текстовое слияние Git, а не семантический редактор метаданных. Близкие
правки одного XML могут потребовать ручного разрешения. После успешного
слияния проверяется полнота дерева XML, затем обычные проверки адаптера и
обратная сверка ibcmd-rs. Некорректное дерево или неподдержанное изменение
не отправляется в хранилище. `ConfigDumpInfo.xml` берётся из полученной версии.

Сквозная матрица одновременных правок проверена на двух независимых копиях
одного тестового хранилища, с раздельными кэшами и XML-основами:

| Сценарий | Без Git | С Git |
| --- | --- | --- |
| Разные объекты | Отказ по устаревшей основе, затем ручной перенос обеих правок | Автоматическое объединение |
| Разные файлы одного объекта | Новая серверная основа и ручной перенос локального файла | Автоматическое объединение комментария корня и модуля сеанса |
| Один файл с обеих сторон | Отказ по устаревшей основе, затем явно собранный итог | Конфликт блокирует подготовку, затем явно собранный итог |
| Удаление против изменения | Отказ по устаревшей основе; в тесте явно принято серверное удаление | Конфликт modify/delete; в тесте явно принято серверное удаление |

Во всех восьми сценариях исходная основа и локальная папка сохранились
побайтно. Итоги проверены независимой выгрузкой Конфигуратора (27–30 файлов
на сценарий). Без Git служебный Git-проект не создавался. Git-сценарии прошли
с `source_branch = "storage/incoming"`: полученные и подтверждённые версии
попали в указанную ветку, ветка по умолчанию не создавалась. Принятие удаления —
явное решение только теста, автоматического выбора победителя в библиотеке нет.

При сохранении прежнего XML учитываются версии потоков всех объявленных
внутренних UUID, включая UUID корня и вложенных команд. Неизменённое тело
владельца больше не маскирует добавление, изменение или удаление такого потока.
Регрессионный тест отдельно проверяет модуль сеанса с UUID внутреннего объекта.

Для неизменённых нативных объектов и потоков сохраняется прежнее представление
XML. Это предотвращает ложные изменения служебных ID форм при разных правилах
экспорта Конфигуратора и ibcmd-rs. Изменённые данные экспортируются из нового CF.

Отдельное согласование без помещения:

```bsl
Результат = Клиент.СогласоватьВыгрузкуСХранилищем(
    "C:\work\target", "C:\work\baseline", Компилятор, "C:\Python39\python.exe");
// merged, report_file, source_branch, repository_commit, git_directory
// При успехе: directory, baseline_directory, work_branch, work_commit.
```

Общий `ПодготовитьКонфигурациюИзВыгрузки` вызывает этот этап при настройке
`use_git = Истина` и использует согласованные папки. По умолчанию Git отключён.
Явный вызов `СогласоватьВыгрузкуСХранилищем` всегда использует Git; вместо
исходной папки можно передать `Неопределено`, чтобы взять сохранённую основу. Git-коммиты имеют технического автора CRS API. Отправка
в удалённый Git и фоновое наблюдение не выполняются. Если между обновлениями
прошло несколько версий хранилища, сохраняется полученный снимок; восстановление
всех пропущенных промежуточных версий ещё не подключено. Рабочие копии и ветки
согласования автоматически не очищаются.

Входящие изменения проверены совместно с автоматическим продвижением основы:
другой пользователь изменил модуль формы, локально изменён комментарий
справочника. Согласование сохранило обе правки, а пакет содержал только
локальное изменение. При конфликте комментария подготовка прекратилась,
активная основа и рабочие файлы сохранились. После разрешения через новую
исходную папку из отчёта помещение и продвижение прошли успешно; принятая
версия сразу появилась в служебной Git-ветке.

На изолированном хранилище получена версия 3; другой тестовый пользователь
изменил модуль формы и создал версию 4. Локальная правка комментария справочника
от старой основы объединена с ней и помещена как версия 5. Обе правки сохранены,
посторонние нативные записи не изменились. Версии 3, 4 и 5 автоматически
зафиксированы в ветке хранилища. Итоговый CF принят Конфигуратором, обе правки
подтверждены его XML-выгрузкой. Отдельный конфликт комментария записан в отчёт
и блокирует подготовку помещения; исходные папки сохранены.

Конечный CF побайтно совпал с исходным по всем записям, кроме служебного списка версий.
Нативные тела и поток сервиса сохранены в тестовых эталонах для общего читателя и CF-delta.

Создание отдельной подсистемы верхнего уровня и её удаление прошли помещение;
Конфигуратор принял созданный объект. Создание вложенной подсистемы через `cf load`
теряет запись ребёнка в CF, а изменение не создаёт нужную запись. В общем входе
эти случаи теперь проходят через полную сборку ibcmd-rs, описанную выше.
Пакеты неудачных попыток не отправлялись серверу. Компилятор чувствителен также
к оформлению XML: остаточные пробелы вместо штатной пустой коллекции могут
вызвать отказ обратной сверки. Проверки компилятора не отключаются.

Карта структуры выделяет 95 маршрутов отдельно хранимых дочерних объектов,
достижимых от Configuration. У 93 UUID класса известен из карты схемы.
Для Recalculation у CalculationRegister и PaletteColor у Configuration добавлено
общее определение класса по единственной коллекции CF с точно совпадающим
набором дочерних UUID. Пустые и неоднозначные коллекции не используются для
определения; противоречия между схемой, CF и серверным классом отклоняются.
Эта проверка не преобразует XML-свойства и не заменяет ibcmd-rs.

Механизм проверен на нативных данных сохранённой тестовой конфигурации:
при отключённых константах классы всех 13 дочерних объектов восстановлены;
идентичности и непустые коллекции 14 объектов совпали с обычным чтением.
Модульные тесты дополнительно проверяют определение класса пересчёта,
создание первого и удаление последнего ребёнка с определяемым классом у корня.
Для обоих классов также выполнен сквозной TCP-сценарий на копии хранилища:
созданы план видов расчёта, регистр расчёта и его первый пересчёт; отдельно
удалён последний пересчёт при сохранении регистра. Затем созданы первый цвет
палитры и его последующее удаление, тестовые родители удалены. Для каждого
нового класса совпали класс и родитель серверного снимка с определёнными по CF.
Конфигуратор 8.5.1.1529 загрузил четыре CF и подтвердил объекты, их UUID,
пустую коллекцию пересчётов и значение цвета `#FFEC9D` своей XML-выгрузкой.
Исходные прикладные файлы восстановлены; посторонние нативные объекты и потоки
сохранились побайтово. Регрессионные тесты используют эти нативные данные,
включая определение класса и проверку пустой коллекции на обеих границах.
TCP-сценарий создания и удаления пересчёта проверен без измерений и модуля
набора записей. Наличие маршрута
в [карте модулей](module-map.md#коллекции-дерева-конфигурации) не подтверждает
поддержку всех свойств и модулей соответствующего класса.

Отдельная семантически связанная конфигурация с измерением пересчёта, ведущими
данными, документом-регистратором и зависимостью плана видов расчёта по периоду
регистрации принята Конфигуратором 8.5.1.1529 из XML и выгружена в CF и XML.
Проверены идентичности и полнота активов всех 14 объектов этого CF.
Штатный `Ext/RecordSetModule.bsl` пересчёта хранится в его нативном потоке `.0`;
маршрут добавлен в общий классификатор модулей и проверку полноты экспорта.
Отсутствие этого BSL в выгрузке при непустом нативном модуле запрещает подготовку.

Для этой валидной конфигурации остаются два подтверждённых ограничения
ibcmd-rs 0.4.1: `cf export` пропускает модуль пересчёта; `cf bootstrap`
также теряет BSL при пересборке собственной XML-выгрузки, в которую возвращён
штатный файл модуля. Значение `OnRegistrationPeriod` свойства
`DependenceOnCalculationTypes`, записанное Конфигуратором, не поддерживается
компилятором. Его вариант `OnBasePeriod` платформа отклоняет. Отказ здесь означает
пробел поддержки компилятора; проверка полноты не позволяет потерять модуль
при инициализации основы или подготовке помещения. Сквозное помещение пересчёта
с этим модулем через XML пока не подтверждено.
Отчёты компилятору: [потеря модуля пересчёта — #708](https://github.com/Untru/ibcmd-rs/issues/708),
[значение зависимости по периоду регистрации — #709](https://github.com/Untru/ibcmd-rs/issues/709).

Для повторной проверки новой сборки компилятора есть отдельная команда:

```powershell
python tools/check_ibcmd_contract.py --executable C:\tools\ibcmd-rs.exe `
  --native-cf C:\lab\native.cf --xml C:\lab\native-xml `
  --platform 8.5.1.1529 --report C:\lab\compiler-contract.json
```

Входы — CF и полная XML-выгрузка одной версии конфигурации, заранее проверенные
платформой. Команда независимо проверяет исходные идентичности и активы CRS,
полный экспорт CF и полную сборку XML с последующим экспортом. Один отказ
не скрывает другой. В отчёте — ошибки по этапам, SHA-256 исполняемого файла и CF,
отпечаток XML и проверка неизменности входов. Временные данные удаляются,
исходные файлы и хранилище команда не меняет. Код завершения: 0 — контракт
прошёл, 1 — есть несовпадение или отказ, 2 — ошибка входов/запуска. Отчёт
нельзя записать внутрь входной XML-папки или поверх CF/компилятора.
Диагностика проверяет конкретную пару; она не заменяет проверку валидности
конфигурации платформой и не подтверждает поддержку всех классов.

## Дальнейшая работа

Расширение получения истории изменений и постоянного кэша истории отложено.
Основное направление — валидные изменения полного XML-проекта через общий
компилятор и пакет помещения.

1. Расширять адаптер результата ibcmd-rs: классы, потоки и зависимости.
2. Расширить сквозную матрицу создания и удаления остальных классов и дочерних
   объектов через общий механизм; для пересчётов добиться полной компиляции
   валидной конфигурации с измерениями и модулем набора записей в ibcmd-rs.
3. Расширить контракт форм и реквизитов без собственных правил записи.
4. Повторить матрицу типов после исправлений ibcmd-rs.
5. Проверить другие платформы. Для старых 8.x предполагается совместимость
   профиля 8.5.1; полная совместимость не доказана.

Общий вход дополнительно проверен на первом реквизите и первой табличной части
документа. Полная сборка ibcmd-rs прошла TCP-помещение и проверку Конфигуратором
для ToolTip реквизита документа и смены EnumRef на Строка(64) параметра сеанса.
Зависимость от перечисления исчезла из пакета и метаданных сервера; структурная
связь с родителем сохранилась.

Переименование документа с тем же UUID проверено вместе с каталогом его форм,
именами генерируемых типов и ссылкой главного реквизита формы. Служебные
описания берутся из исходного снимка до изменения имени; известный именной
суффикс обновляется, пустое описание из кэша остаётся пустым. Класс и родитель
существующего UUID по-прежнему не меняются.

Переименование реквизита справочника с сохранением UUID проверено через общий
TCP-пакет вместе с обновлением DataPath в полном XML формы; обратным помещением
восстановлено исходное имя. Серверный снимок сохранил UUID возможности реквизита,
Конфигуратор 8.5.1.1529 подтвердил имя и путь поля формы в обе стороны.
Изменился только нативный справочник: поток формы сохранился побайтово, поскольку
привязка к реквизиту определяется его идентичностью. При обратном экспорте новый
путь формы получается из итогового владельца. В пакет вошёл один объект без
созданий и удалений; посторонние записи CF сохранились. Регрессионные тесты
проверяют общий контракт для неизменённого потока формы и отклоняют DataPath
из другой версии владельца. Переименования остальных классов ещё не имеют
отдельной сквозной проверки.

Через общий TCP-вход проверены добавление табличной части справочника с четырьмя
реквизитами и таблицей управляемой формы, переименование вложенного реквизита
с обновлением DataPath, затем удаление добавленной части и элементов формы.
Конфигуратор 8.5.1.1529 загрузил и независимо выгрузил все три итоговых CF.
UUID табличной части, реквизита и генерируемых типов сохранились при переименовании;
изменился только справочник, нативный поток формы остался прежним. Прикладные
файлы восстановлены обратным помещением. Для таблицы использован полный XML,
выгруженный платформой, со штатными контекстными меню и дополнениями: минимальный
вручную составленный Table без ContextMenu ibcmd-rs 0.4.1 отклоняет.

Читатель табличных частей охватывает все десять владельцев внутри конфигурации:
справочник, документ, обработку, отчёт, ПВХ, ПВР, план счетов, план обмена,
бизнес-процесс и задачу. Профили выбираются по карте метаданных, независимо от
наличия старого профиля свойств объекта. Для пяти добавленных владельцев нативная
структура подтверждена отдельной XML-загрузкой и CF/XML-выгрузкой Конфигуратора
8.5.1.1529; проверены табличная часть с четырьмя реквизитами (Строка, Число,
Булево, ДатаВремя), главный реквизит формы и таблица с четырьмя колонками.
Запись свойств по-прежнему целиком выполняет ibcmd-rs.

| Владелец | Результат дополнительной проверки табличной части и формы |
| --- | --- |
| Бизнес-процесс и задача | Полная сборка ibcmd-rs, TCP-создание обоих владельцев с формами, переименование реквизитов с сохранением UUID, удаление табличных частей и обратное удаление владельцев; все итоговые CF подтверждены Конфигуратором |
| ПВР и ПВХ | Раздельные полные сборки ibcmd-rs, совместное TCP-создание владельцев с формами, переименование реквизитов, удаление табличных частей и обратное удаление владельцев; все итоговые CF подтверждены Конфигуратором |
| План счетов | Нативная конфигурация валидна; ibcmd-rs 0.4.1 не сохраняет табличную часть при полной обратной выгрузке. Подготовка помещения отклоняется |
| План обмена | Нативная конфигурация валидна; overlay отвергает изменение, после bootstrap отсутствует XML владельца при сохранённой ссылке в корне. Проверка полноты отклоняет результат |

Новые профили привязок бизнес-процесса, задачи, плана обмена и ПВР подтверждают
главный реквизит, обычные реквизиты и пути табличных частей; стандартные реквизиты
этих владельцев отдельно не подключены. Внешние обработки и отчёты не являются
объектами дерева конфигурации и этой матрицей не покрываются. Регрессионные тесты
проверяют нативные UUID и скалярные типы колонок, запрещают путь к ещё не созданной
табличной части, чужой тип главного реквизита и повреждённую коллекцию.
В обеих TCP-последовательностях сохранены UUID при переименовании и посторонние
нативные записи; прикладные файлы и исходный состав захватов восстановлены.
В полном наборе Python-проверок после расширения профилей — 370 успешных тестов.

Для обычных реквизитов этих четырёх владельцев независимо подтверждены нативные
Строка(80), Число(15,3), Булево, ДатаВремя и ссылка на собственный объект, вместе
с пятью полями формы. Используется существующий общий читатель `inline_groups`;
новых правил записи свойств нет. Полные сборки ibcmd-rs с обратной проверкой
всего XML и графа идентичностей прошли для бизнес-процесса, задачи и ПВР.
План обмена с табличной частью по-прежнему блокируется отсутствием XML владельца
в обратной выгрузке компилятора. Регрессионные тесты проверяют UUID каждого
поля, собственный Ref-тип владельца и отказ при отсутствующих реквизитах,
повторном UUID или неверном классе коллекции.

Через общий TCP-вход дополнительно проверены создание бизнес-процесса, задачи
и ПВР с этими реквизитами, табличными частями и формами, переименование обычного
реквизита с обновлением DataPath, смена его типа Строка(80) → Число(10,2),
удаление пяти обычных реквизитов и полей формы, затем обратное удаление владельцев.
После каждого помещения полученные с сервера тела и потоки сверены с пакетом
при продвижении основы. Все итоговые CF независимо загружены и выгружены
Конфигуратором 8.5.1.1529. UUID обычных реквизитов сохранились при переименовании
и смене типа; посторонние нативные записи не изменились, прикладные файлы и
исходные захваты восстановлены.

Все 29 файлов на этапах смены типа, ToolTip и переименования совпали с независимой
выгрузкой Конфигуратора. Временные перечисление и параметр удалены; имя документа,
ToolTip и исходная конфигурация восстановлены отдельным помещением.
