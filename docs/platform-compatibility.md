# Профили совместимости платформы

Номер платформы в HTTP-запросах остаётся фактическим номером, переданным
в конструктор `КлиентХранилища`. Профиль определяет алгоритм работы библиотеки,
а не подменяет версию клиента или сервера.

Правила находятся в `СовместимостьПлатформы.os` и `platform_profiles.py`:

| Версия | Профиль |
| --- | --- |
| Ветка 8.5.1 с любым номером сборки и все более ранние версии 8.x | legacy, поведение 8.5.1 |
| 8.5.4.1878 | modern, ранее проверенное поведение 8.5.4 |
| Остальные более новые версии | Профиль XML-сериализации не определён |

Версия разбирается как четыре числа, а не сравнивается как строка. Некорректные
номера и другие основные версии отклоняются. Это правило используется для
подготовки XML, проверки пакетов создания, чтения статистики и отмены захвата.
Остальные методы хранилища продолжают передавать указанный номер версии.

Для legacy выбираются общие свойства формата 3, таблица свойств корня 76/77
и проверенный шаблон простого справочника. Принимаются XML-ревизии `2.0`–`2.21`
в прежнем пространстве имён либо XML без атрибута версии. Содержание XML,
снимки, отношения, UUID, исходные версии и размеры таблиц проверяются отдельно.
Несовместимая структура приводит к отказу до отправки помещения, без попытки
исправить её произвольной перестановкой полей.

Для чтения версии объекта legacy запрашивает полную статистику. При отмене
захвата дополнительная выборка по UUID получает номер версии захвата; проверки
владельца и версии содержимого сохраняются.

На реальном хранилище подтверждены 8.5.1.1529 и ранее 8.5.4.1878. Использование
legacy на более ранних версиях — допущение совместимости по запросу пользователя,
а не результат проверки каждой сборки. Синтетические тесты проверяют выбор
профиля, формирование запросов и пакетов для 8.5.1.1150, 8.5.0, 8.3 и 8.2,
а также отказ для несовместимых структур. Алгоритм нативного хеша версий всё ещё
не восстановлен; XML-сериализация остаётся экспериментальной.
