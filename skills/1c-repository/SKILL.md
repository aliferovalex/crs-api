# Хранилища 1С через CRS API

Если MCP CRS API подключён, используй его инструменты напрямую: `crs_connect`,
`crs_objects_search`, `crs_objects_read`, `crs_workspace_init`, `crs_changes_prepare`,
`crs_modules_prepare`, `crs_changes_plan`, `crs_changes_status`, `crs_users_list`, `crs_users_plan`. Передавай `profile` и параметры действия
без оболочки `schema/action/params`; результат CLI находится в `structuredContent`.
Проверяй `isError` и `ok`, включая ошибки преобразования в результате чтения.
Относительные пути разрешаются в `--workspace` сервера. `crs_users_apply` доступен
только при запуске с `--allow-user-writes`; это не заменяет одобрение операции.
Установка, передача пароля и проверка прямых вызовов описаны в
[руководстве MCP](../../docs/mcp-install.md); при установке MCP прочитай его
раздел «Для агента». Контракты — в [MCP-сервер](../../docs/status.md#mcp-сервер).
Если инструменты отсутствуют в текущем чате, сообщи об этом; успешный запуск
CLI не означает успешного подключения MCP к чату.

Если MCP не подключён, используй тот же контракт через CLI:
`python tools/crs.py --config CONFIG --request REQUEST.json`.
Пути в команде разрешай относительно корня CRS API, а не текущей папки агента.
CLI принимает один UTF-8 JSON и возвращает один JSON; ненулевой exit code означает
ошибку. `--request -` читает stdin. `--help` возвращает JSON со списком действий.
При установке навыка отдельно от исходников найди checkout по `CRS_API_HOME`
или указанному пользователем пути; CLI и документация остаются в этом checkout.

Формат запроса, настройки и ограничения описаны в
[docs/status.md](../../docs/status.md#json-cli).
Образец конфигурации: [examples/cli.config.json](../../examples/cli.config.json).
Выбирай именованный профиль из настроек пользователя. Не угадывай production-адрес
и не включай реальные адреса, логины или пароли в этот навык. Пароли CLI получает
из переменных окружения; не печатай их, хеши или полный файл чужих настроек.

## Чтение и поиск

- Начни с `connect`, затем `objects.search` по имени или `kind`.
  Это поиск актуальных описаний отдельно хранимых объектов, не полнотекстовый поиск BSL.
- `objects.read` по UUID возвращает нативное содержимое и, при `format="xml"`,
  читаемые XML/BSL через ibcmd-rs. Проверяй `representation.status`: `unavailable`
  означает ошибку преобразования, а не отсутствие кода. Нативное содержимое остаётся
  доступно. Для получения потоков без компилятора используй `format="native"`.
- Результат фиксирует версию хранилища. При конфликте чтения повтори получение
  свежего состояния; не смешивай файлы разных версий. Корневой объект читается
  без неявной выгрузки всей конфигурации; контекст одного объекта ограничен.

Пример:

```json
{"schema":1,"action":"objects.search","profile":"test","params":{"kind":"CommonModule","query":"Обмен","limit":20}}
```

## Локальная доработка

Для одного существующего отдельно хранимого BSL-модуля используй
`crs_modules_prepare` (`modules.prepare` в CLI): `object_id`, точный `module_path`,
`source_file`, `expected_source_sha256`, новый `output_directory` и профиль.
Это адресное чтение и локальная компиляция через ibcmd-rs, без полной конфигурации
и кэша. Хеш берётся из исходного BSL, на котором основаны правки: UTF-8 без BOM,
переводы строк сохраняются. При несовпадении сначала согласуй изменения;
не заменяй ожидаемый хеш свежим только для обхода конфликта. Модули форм этим
путём не поддерживаются. Изучи `plan.diff` и результат `has_changes`;
no-op возвращает `packet_file=null`. [Контракт](../../docs/status.md#адресная-подготовка-bsl-модуля).

При большой конфигурации учитывай `limits` профиля: это защитные бюджеты CRS,
а не пределы 1С. Инициализация кэша и источник подготовки используют файлы вместо
общего XML/base64-буфера. При ошибке размера определи конкретный слой и его ключ;
не отключай контроль целостности ради загрузки. Для прямого OneScript смотри
[политику процесса и файловый API](../../docs/status.md#размеры-и-защитные-лимиты).

`workspace.init` создаёт XML-основу и рабочую папку из хранилища. Для полного поиска
по коду используй локальную рабочую папку. Сохраняй основу отдельно от правок.

После редактирования полных XML/BSL-файлов используй `changes.prepare`.
Он компилирует через ibcmd-rs, сохраняет `packet.bin` и `review.json` в новую папку
и возвращает план и diff. Изучи удаления, связанные объекты и ограничения
компилятора. Проверки компиляции не означают выполнение прикладного кода на данных.
Не заменяй ошибку подготовки скрытой записью через другой транспорт.

Для помещения вызови `crs_changes_plan` с каталогом подготовки и комментарием.
Изучи diff и план: профиль, UUID хранилища, исходные версии, изменения, удаления,
состояния захватов, комментарий и метку. Получи явное одобрение этого конкретного
плана перед захватом и помещением. Затем `crs_changes_commit` принимает `plan_file`,
точный `approved_plan_sha256` и `execute=true`; инструмент доступен только с
`--allow-configuration-writes`. Включение инструмента не заменяет одобрение.
Для Jira соблюдай проектный формат комментария `#KEY: описание` и метки `#KEY`.
Запись меток пока не поддерживается: не объявляй её выполненной, даже если
`committed=true`. Проверяй также `readback_verified`, `fully_completed`, состояние
основы и захватов. При ошибке, обрыве или `outcome_unknown` используй только
`crs_changes_status` с `plan_file/plan_sha256`; автоматический повтор помещения
запрещён. Существовавшие до операции собственные захваты сохраняются.
Старые пакеты без `prepared.json` нужно подготовить заново.

## Пользователи

Сначала выполни `users.list`; в ответе нет паролей и хешей. Для изменения используй
`users.plan` с `operation`: `create`, `update`, `delete` или `restore`.
Роли: `read_only`, `developer`, `developer_extended`, `admin`.
Создание по умолчанию использует `read_only`. Для нового пароля передавай имя
переменной `password_env`; отсутствие этого поля при update сохраняет пароль.

Покажи профиль, конкретного пользователя, роль, действие и признак смены пароля.
Получай явное одобрение именно этой операции до `users.apply` с `execute=true`.
Для update/delete/restore передай `before` из плана как `expected`.
Он включает исходную маску `rights`. Неизвестные маски не означают чтение;
при обновлении имени/пароля без `role` существующие права сохраняются полностью.
Общее разрешение читать хранилище не разрешает менять пользователей. Запрос
создать CLI или навык также не является разрешением на изменение реального храна.

При `user_conflict` перечитай состояние и подготовь новый план. При `outcome_unknown`,
таймауте или обрыве после записи сначала проверь пользователя; не повторяй запись
автоматически. Проверка ожидаемого состояния не является серверной атомарной CAS.
Не выводи секреты при диагностике отказа и не считай пустой список признаком
успешного запроса, если CLI вернул `ok=false`.

В ответе отделяй прочитанное, подготовленное локально и действительно выполненное.
